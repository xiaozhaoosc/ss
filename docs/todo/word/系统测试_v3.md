# 5 系统测试

任何软件工程项目在正式进入生产环境（Production Environment）并交付给终端用户之前，都必须经历详尽而严苛的测试。对于“小步”系统而言，由于其目标群体的特殊性（儿童）及数据的高隐私敏感度，系统的稳定性、安全性和交互防错能力显得尤为重要。本章将详细描述系统的测试环境搭建、从核心功能逻辑到性能抗压的多维度测试方案及其实际运行结果分析。

## 5.1 测试环境与策略构建

### 5.1.1 测试环境说明
为保证测试结果的可靠性与拟真度，本次测试构建了独立的预发布回归环境：
1.  **后端服务端环境**：使用 Docker 容器化运行 PostgreSQL 15 数据库与 Redis 7，保证了与开发环境及生产环境的数据隔离性。后端 Spring Boot 应用打包为 jar 独立运行。
2.  **前端及终端环境**：移动端打出了面向 Android 的 `.apk` 包和 H5 测试包，主要在华为 P40 Pro 和 Mate 30 Pro 真机上进行功能和兼容性验证。管理后台终端通过最新版的 Google Chrome 浏览器进行访问测试。

### 5.1.2 测试维度设计 (功能、交互、兼容性)
测试规划依据以下三大核心维度展开：
1.  **功能逻辑验证（黑盒测试）**：确认业务核心流转——从“家长建任务 -> 儿童接收 -> 执行完成 -> AI 反馈生成”的完整闭环没有逻辑挂起或断点。
2.  **UX 交互测试**：模拟各类非常规的用户操作（如：频繁连击按钮、专注途中突然锁屏或返回），验证防错机制（Graceful Degradation）是否生效，保障系统的用户体验底线。
3.  **兼容性与网络测试**：测试不同屏幕尺寸的 UI 渲染情况，以及在弱 Wi-Fi 信号下本地倒计时和离线缓存的有效性。

## 5.2 核心业务功能测试

### 5.2.1 多角色权限与路由防越权测试
**测试目标**：验证 Sa-Token 在处理同一家庭群组及跨家庭群组身份时的横向及纵向越权防御机制。

**测试执行与结果**：
1.  **【场景 A：纵向越权防御】** 使用儿童端账号的 Token，直接通过 Postman 或控制台尝试发起 POST 请求访问 `/ssapi/parent/task/create`（仅限家长权限的建任务接口）。
    *   **结果**：请求被后端响应体拦截，HTTP 状态码返回 403 Forbidden，系统抛出自定义异常提示“权限不足”。符合预期。
2.  **【场景 B：横向越权防御（租户隔离）】** 使用家长甲的有效 Token，修改请求参数尝试获取家长乙名下儿童的打卡日历数据。
    *   **结果**：请求被底层的 MyBatis-Plus 拦截器结合权限上下文识别出数据不属于当前操作人，返回空数组或“非法访问”提示，说明横向防越权的数据隔离设计切实有效。符合预期。

### 5.2.2 任务生命周期状态扭转测试
**测试目标**：覆盖任务实例（Task Log）在各个关键节点的状态流转正确性。

**测试执行与结果**：
在移动端完整走通以下流转并查询后台数据库对照：
1.  **【创建与下发】** 在家长端建立一条“限时执行 5 分钟”的扫地任务。儿童端下拉刷新后即可看到对应的待办卡片。此时查询数据库，该任务记录的初始状态为待办（`status=0`）。
2.  **【状态切入与挂起】** 儿童端点击该卡片的“开始专注”按钮，倒计时正常启动。查询数据库，状态准确变更为进行中（`status=1`）。在此过程中，将应用切换至后台挂起，50秒后再次唤醒，页面时间依旧按自然时间差准确递减，未出现应用被杀或时间冻结的错误。
3.  **【打卡结算】** 倒计时计满，系统自动播放成功音效，并弹出获得代币动画，随后自动发起提交流水。查询数据库，状态变更为已完成（`status=2`），并且 `ss_child` 表中的代币余额（`star_balance`）和 `ss_star_record` 流水表记录均同步更新且数值对应。
    *   **结论**：任务全生命周期的推演完全符合产品需求定义，分布式事务控制与数据回溯表现完整。

### 5.2.3 专注模式防误触与容错测试
**测试目标**：验证应用对儿童不可预测的点击和滑动行为的容错处理能力。

**测试执行与结果**：
1.  **【返回键拦截】** 在专注倒计时进行中，测试人员按下安卓设备的物理返回键或进行屏幕左滑手势。
    *   **结果**：系统成功拦截了返回动作，并弹窗提示“确认放弃？现在退出专注将失去当前奖励碎片”。只有在点击确认后才允许退出，有效防止了误触导致的任务失败。
2.  **【高并发防抖连击】** 任务完成弹窗出现时，测试人员以极快速度连续点击“领取奖励”按钮5次。
    *   **结果**：前端防抖逻辑加上后端的 Redis 分布式互斥锁（SETNX）成功拦截了后续的 4 次无效请求。代币余额仅增加了一次，防止了因网络延迟导致的奖励重复核发（Double Spending）漏洞。

## 5.3 本章小结
本章对“小步”系统进行了严密的回归测试验证。我们首先搭建了独立且数据隔离的预发布测试环境，并确立了功能、交互与兼容性三大测试维度。通过对最核心的“多角色防越权”、“任务全生命周期流转”以及“专注模式容错与防连击”等典型用例进行实机执行，系统均给出了符合预期的结果。测试数据表明，系统在 Sa-Token 保护下的权限隔离稳定可靠，Spring Boot 事务和 Redis 互斥锁也经受住了异常操作的考验。系统整体达到了设计初期的功能目标和稳定性要求，具备了实际落地的交付条件。
