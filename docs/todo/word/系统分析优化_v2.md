# 2 系统分析

在明确了系统的业务目标和相关的开发技术之后，本章将从系统的可行性入手，深入剖析目标用户的核心痛点，并在此基础上详细阐述系统在交互功能及非功能性能维度的具体需求规格，为后续的系统架构与数据库设计奠定基础。

## 2.1 可行性分析
“小步（Small Steps）”系统的研发在工程实施、操作体验与理论指导三个方面均进行了严谨的考量，以确保项目的顺利落地与后续的稳定运营。

### 2.1.1 技术可行性
系统基于标准的 B/S（Browser/Server）与 C/S（Client/Server 移动端）混合演进的前后端分离架构，通过 RESTful API 进行松耦合的数据通讯。
*   **后端支撑**：采用成熟的 Spring Boot 3 框架搭配 MyBatis-Plus 数据持久层，二者在 Java 生态中已经过大规模工程验证，具备极高的稳定性和海量的社区支持。
*   **前端展现**：UniApp 3.0 框架可一次编写实现多平台（Android、H5）的适配输出，Vue 3 生态的 Composition API 和 Pinia 状态管理工具链亦已趋于稳定，大大降低了跨端开发成本。
*   **数据保障**：使用广泛采用的 PostgreSQL 关系型数据库存储核心业务数据，辅以 Redis 处理高频缓存与防并发机制，为高并发场景提供了可靠的技术基础。
综合来看，系统选用的技术栈成熟度高，技术方案具备高度可行性。

### 2.1.2 操作可行性
系统面向的终端用户包括 ADHD 儿童（6-15岁）及其家长。
*   **儿童端**：交互设计严格遵循“零认知负荷”原则，采用大字体、大按钮和单线程任务呈现的方式，摒弃复杂的导航层级。操作流程力求直觉化，符合儿童的使用直觉，不要求用户具备任何技术背景。
*   **家长端与管理后台**：家长端的功能布局参照主流移动应用的常见范式，操作逻辑清晰；管理后台采用标准化的 Element Plus 组件库，面向具备基本计算机操作能力的运营人员，操作门槛可控，极易上手。

### 2.1.3 理论指导可行性
系统并非简单的软件堆砌，其核心交互逻辑深度融合了心理学与教育学理论：
*   **认知负荷理论 (CLT)**：通过界面的“认知卸载”设计（单线程呈现、低饱和色彩），释放患儿有限的工作记忆空间。
*   **脚手架理论 (Scaffolding)**：通过 AI 研判实现的渐进式辅助（Fading Strategy），帮助患儿实现从“他律”向“自律”的平稳过渡。
*   **操作性条件反射与系统家庭动力学**：以随机、即时的正向游戏化反馈建立稳固的多巴胺循环，同时通过系统作为“缓冲介质”，将家长的角色从“裁判”重塑为“队友”，从理论底层保证了干预方案在家庭环境中的可行性与长效性。

## 2.2 系统需求分析
需求分析是软件工程流程中的关键环节，它决定了系统建设的边界与最终交付的价值。本节针对“小步”系统的双端目标受众特征进行深度剖析，并推导出相应的功能与非功能需求。

### 2.2.1 目标用户群体分析
本系统的核心服务对象是一个双核架构：即干预的接受者（ADHD 儿童）与干预的辅助实施者（家长或监护人）。

**（1）ADHD儿童与青少年的认知与行为画像**
根据调研，年龄在 6-15 岁区间的 ADHD 学龄群体具有以下显著画像：
*   **注意力短暂且极度受兴趣驱动**：对于高多巴胺刺激（如游戏）能保持极强的专注力，但对日常重复性任务（如洗漱、写作业）的注意力通常维持不到 5-10 分钟。
*   **计划与时间感知盲区**：极度缺乏对“预计耗时”的评估能力，经常表现出严重的拖延或是临近截止时极度慌乱。
*   **情绪波动大与极低挫折抗性**：极容易因为微小的失败而情绪崩溃，或者直接放弃并表现出攻击性抗拒。
基于上述画像，儿童端应用的需求底线是：**零学习成本、极高的容错率、即时且强烈的视觉/听觉奖励**。它必须像一个“懂他们心智的通关游戏”，而非刻板的效率工具。

**（2）监护人的管理诉求与痛点分析**
陪伴 ADHD 患儿成长的家长群体是本系统的另一关键用户。他们的典型痛点包括：
*   **监督疲劳与精力透支**：每天需重复数百次相同的指令，导致情绪耗竭，引发高频家庭冲突。
*   **过程盲盒与“虚假完成”困境**：缺乏对任务完成质量与实际投入时长的系统性量化把控手段。
*   **渴望科学的实操指导**：家长迫切需要能够告诉他们“在孩子此刻情绪崩溃时，我该怎么做”的具体策略，而非泛泛而谈的理论。
因此，家长端的需求中心必须围绕**数据可视化呈现、任务高效分发、以及智能辅助话术**展开，充当家长的“外脑”和“情绪稳定器”。

### 2.2.2 系统功能需求
依据多角色业务流向，系统在功能域上划分为三大相互协同的模块：儿童移动端、家长移动端以及全局管理后台终端。

**（1）核心业务模块流转**
系统业务流程围绕“任务”核心实体展开。家长在管理端创建任务，分配给指定日期的儿童账户；儿童账户接收指令，通过专注模式执行任务，并在完成后触发奖励结算；数据随即回流至服务器并更新至家长端看板；夜间，内置的 AI 模块扫描全天数据，生成建议与总结，准备次日的介入指导。

**（2）儿童端功能需求描述 (执行与反馈层)**
儿童端作为数据产生的触发源头，核心功能极尽精简：
1.  **任务卡片极简展示**：以大字体、高宽容度图标（Icon）按序单线程展示待办任务，支持一键“开始进行”或“暂缓跳过”，避免列表平铺带来的压迫感。
2.  **沉浸式专注模式**：提供正/倒计时工具。计时期间，屏幕屏蔽外界干扰，以可视化的水流或沙漏等微动效具象化“时间的流逝”，减轻患儿的时间流失焦虑。
3.  **即时正向打卡与代币系统**：任务完成后，系统需立即触发绚丽的全屏成功动画，并发放虚拟代币。代币归入进度池，进度可视化，可用于兑换家长预设的心愿礼物。

**（3）家长端功能需求描述 (配置与观测层)**
家长端旨在为家庭管理者提供控制台：
1.  **结构化任务创建与智能模版**：支持新建任务，设置执行周期、奖励代币数及强制前置拆解步骤（支持图文）。系统内置常见“场景模版”（如“晨间洗漱”）供一键引用。
2.  **多维度数据看板**：支持查看孩子每日任务完成率、累计专注时长、各任务平均超时情况。数据以柱状图、环形图等直观呈现，打破传统干预的“黑盒”状态。
3.  **AI 智能生成反馈**：接收由大语言模型（LLM）基于前日数据自动撰写的、旨在安抚儿童情绪与肯定微小进步的“每日寄语”，并支持同步推送给儿童。

**（4）管理后台功能需求描述 (运维与监控层)**
主要供平台运营人员与超级管理员使用，保障系统的良性运作：
1.  **用户与组织机构管理**：实现对家长账号、儿童子账号状态的冻结、解封操作，监控平台日活与异常登录行为。
2.  **公共素材库与模版审核**：管理和维护全局任务预设库、系统内置的奖励图标及表扬音效素材。
3.  **大模型配置与运营监控**：配置对接外部 LLM 的 API 密钥，监控生成 Token 的消耗量，并配置应对模型服务降级或熔断时的兜底话术库。

### 2.2.3 非功能性需求分析
**（1）性能与响应时延要求**
*   **高频打卡接口响应**：考虑到专注模式结束时的状态同步与代币结算涉及跨库事务，核心 API 接口的响应时间需控制在 150 毫秒以内（99th Percentile），确保前端动画衔接无卡顿。
*   **大模型异步处理**：AI 寄语生成伴随较长的网络延迟（10s-30s），此类功能不可阻塞主线程，必须采用定时任务或消息队列异步处理。
*   **并发承载**：晚间为全国中小学生写作业的高峰时段，系统需至少支持单节点 1000 QPS（Query Per Second）的并发请求压力，防止瞬时流量峰值导致系统雪崩进而影响患儿情绪。

**（2）系统安全性与用户隐私保护要求**
*   **未成年人数据隔离**：数据库设计需遵循极小化采集原则，任何包含患儿隐私的信息在入库时必须进行哈希（Hashing）或加密存储。
*   **API 防重放与防篡改**：前端发往后端的核心写操作请求（如任务结算），需经过严密的时间戳校验与请求签名比对，并结合 Redis 防连击锁，杜绝伪造请求“无限刷取代币”的可能。
*   **多角色越权防护**：严格利用 Sa-Token 基于 RBAC 模型进行验证。在路由层和核心业务逻辑层实现双重校验（如强制验证：家长账号仅能查询其绑定的儿童数据），严防纵向或横向越权。

**（3）可用性与兼容性要求**
*   **跨终端一致性表现**：由 UniApp 构建的安装包，在主流 Android 厂商（华为、小米等）设备下，排版（尤其是 TailwindCSS 渲染的异形圆角）需保持一致，并自适应沉浸式状态栏/刘海屏。
*   **弱网抗性保障**：在卧室等 Wi-Fi 信号不稳定的场景下，儿童端核心的“专注倒计时”本地模块绝不应失效。应用须将当前进度离线缓存，待网络恢复后在后台静默发起增量数据同步。

## 2.3 本章小结
本章从系统可行性与需求分析两个维度对“小步”行为习惯辅助系统进行了全面论证。首先，在工程与操作层面论证了前后端分离架构与全平台适配的可行性，并深入探讨了认知负荷理论、脚手架理论及家庭动力学对系统交互设计的底层理论支撑。随后，通过对患儿与家长这一“双核”目标用户群体的痛点解构，推导出了儿童端的“极简执行与即时激励”和家长端的“任务分发与智能观测”核心功能流转闭环。最后，明确了系统在响应时延、大模型异步处理、多角色数据越权防护及弱网抗性方面的非功能性要求。本章的需求抽象与分析结果，为后续的系统总体架构搭建与核心数据库结构设计提供了直接且清晰的蓝图约束。
