ADHD中小学生（儿童）行为习惯辅助系统设计与实现
　　摘要：	注意缺陷多动障碍（ADHD）以注意力维持困难、活动过度及行为冲动为核心表现，是学龄期儿童中较为常见的神经发育性障碍。当今主流之药物干预需长期服药，对儿童身体发育兼具特定影响；辅助性之线下行为矫正则在繁忙之学业安排中使家长与儿童承受较大负担。随着人工智能技术之演进，借助数字化途径实施辅助干预成为可能。围绕认知减负、亲子协同交互及动态激励等中枢中枢诉求，本文规划设计并落地了一套面向ADHD中小学生之行为习惯养成综合辅助平台底层架构——“小步（Small Steps）”。平台底层架构依托前后端分离底层架构，经由儿童端、家长端与管理后台之三端协同；搭建涵盖渐进式任务拆解、多模态激励与情绪追踪之数字化干预闭环。技术层面，后端立足于Spring Boot 3与MyBatis-Plus搭建；选用Sa-Token落地多角色鉴权，以PostgreSQL与Redis作为数据存储与缓存方案；移动端依托UniApp与Vue 3落地双模式动态切换。平台底层架构之中枢创新在于集成大语言范式模型（LLM），经由剖析儿童行为数据动态生成个性化激励话术与干预建议；缓解执行疲劳，并引导家长从”监督者”转变为”陪伴者”；为ADHD日常数字辅助干预赋予了一种新之实践路径。

　　Design and Implementation of ADHD Behavior Support System for Children
　　Abstract: 	Attention deficit hyperactivity disorder (ADHD), characterized by difficulties in sustaining attention, hyperactivity, and impulsivity, is a prevalent neurodevelopmental condition among school-age children. Mainstream pharmacological interventions require long-term administration and may adversely affect physical development, while supplementary offline behavioral therapies often impose substantial burdens on both parents and children amid demanding academic schedules. With the advancement of artificial intelligence, digital tools have emerged as a viable modality for assisted intervention. Addressing core needs such as cognitive offloading, parent-child coordination, and dynamic motivation, this study designed and implemented a comprehensive habit-formation support system for elementary and middle school students with ADHD, named "Small Steps." The system adopts a front-end/back-end separation architecture, integrating a child application, a parent application, and an administrative backend to establish a digital intervention loop encompassing progressive task decomposition, multimodal incentive mechanisms, and emotion tracking. On the technical side, the backend is built upon Spring Boot 3 and MyBatis-Plus, employing Sa-Token for multi-role authentication, with PostgreSQL and Redis serving as the data persistence and caching layers. The mobile application utilizes UniApp with Vue 3 to enable dynamic dual-mode switching. The principal innovation of the system lies in the integration of a large language model (LLM), which dynamically generates personalized motivational messages and intervention recommendations by analyzing children’s behavioral data—alleviating execution fatigue and guiding parents to transition from "supervisors" to "companions," thereby offering a novel practical approach for daily digital-assisted ADHD intervention.
　　Keywords:	ADHD; Behavioral Intervention; Spring Boot 3; UniApp; Vue 3

1绪论
　　注意力缺陷多动障碍（ADHD）是学龄期儿童中最为常见之神经发育性障碍之一。其中枢症状表现为注意力维持困难、活动量异常偏高暨行为冲动性增强。针对正处于中小学阶段之患儿而言，上述症状所带来之影响是多维度之：课堂学习效率显著下降；日常生活自理能力局限性，家庭关系亦随之趋于紧张。现阶段主流之干预途径囊括药物治疗与线下行为矫正两类，但药物兼具特定之副作用风险；线下矫正则受限于专业资源稀缺与经济成本较高，并非所有家庭均能持续承担。近年来，随着物联网与人工智能技术之快速演进；数字疗法逐渐成为ADHD干预领域之新方向。然而，当今市面已有之应用实践程序大多仅赋予基础之时间管理或番茄钟职能；专门面向ADHD儿童特质开展平台底层架构性规划设计之软件产品仍然较为匮乏。
1.1研究背景
　　注意缺陷多动障碍（Attention Deficit Hyperactivity Disorder，简称ADHD）；全球学龄儿童之发病率约为5%至7%[1]，环节地区之统计数据甚至更高。其中枢症状表现为：与同龄人相比，注意力维持能力显著局限性、活动水平异常偏高、行为控制能力薄弱。亟待指出之是，上述症状通常不会直接影响儿童之智力水平；但对其”执行职能”之损害却是显著之——囊括工作记忆容量下降、情绪调节能力减弱、内在动机局限性暨计划组织能力受限等[2]。
　　在日常学习与生活场景中，ADHD儿童面临之困难远超一般认知。课堂上难以持续专注、易受外界干扰分散注意力属于常见表现，家庭作业场景中则普遍兼具任务启动困难、执行拖延、无法自主分解任务步骤等痛点。在社会交往层面，因冲动控制能力局限性；患儿容易出现插话、打断他人甚至肢体冲突等行为，进而导致同伴排斥与社会孤立。长期处于这种反复受挫之环境中，儿童极易孕育低自尊、焦虑及抑郁等继发性心理痛点[3]。由此可见，如何有效辅助ADHD儿童在日常生活中减轻认知负荷、逐步确立规律化之行为习惯；已成为一项具有现实紧迫性之社会议题。
1.2研究目的
　　常规之ADHD干预途径中枢囊括药物治疗与行为干预两种路径。药物方面，以利他林为代表之中枢兴奋剂虽能在特定程度上缓解中枢症状；但在儿童群体中之应用实践始终兼具争议——食欲减退、睡眠障碍、对身高发育之潜在影响等痛点令不少家长望而却步。行为干预方面，以家长管理培训（Parent Management Training）为代表之非药物疗法在长期效果上已获得实证支持；但其实施门槛较高：非但亟待专业心理治疗师之持续指导，更要求家长在日常生活中长期、稳定、科学地执行干预路径。然而现实中，家长自身已承受较大之工作与生活压力；且多数缺乏平台底层架构之心理学训练，在反复督促孩子完成任务之进程中极易孕育情绪耗竭。其成效往往是痛点未能有效应对，亲子关系却先行恶化；陷入相互消耗之恶性循环[4]。
　　在此背景下，数字化辅助工具之价值日益凸显。移动应用实践程序兼具全天候在线、情绪稳定、数据记录精确等天然显著优势，将其引入ADHD家庭之干预场景中；能够充当亲子之间之”中介缓冲层”。一方面，应用实践程序能够经由游戏化规划设计与即时反馈运作机制；为多巴胺分泌水平偏低之ADHD儿童赋予高频、正向之刺激，将原本枯燥之日常任务转化为具有特定趣味性之活动；另一方面，应用实践程序能够替代家长承担环节监督职能；削减亲子之间因任务督促孕育之直接语言摩擦。当家长从监督任务完成之焦虑中解脱出来后，便能将更多精力投入到情感支持与高质量陪伴中；从而改善家庭整体氛围。
1.3研究意义
　　当今应用实践市场中以”日程管理”、”时间追踪”、”番茄钟”为名之效率类应用实践程序数量众多，但将其应用实践于ADHD儿童群体时；普遍兼具适配性局限性之痛点。具体而言，兼具以下几方面缺陷：
　　1. 认知负荷过高。通用型应用实践程序为追求职能丰富性，往往在界面中密集呈现图表、菜单与多层级导航。针对执行职能本身已受损之ADHD儿童而言，这类视觉与认知层面之信息过载极易引发回避行为；使其尚未开始运用便已孕育畏难情绪。
　　2. 任务分解粒度局限性。ADHD儿童面临之中枢困难之一是任务启动障碍——当他们面对"写作业"这类整体性任务时，往往因无法自行拆解步骤而陷入停滞。通用工具鲜少赋予将复杂任务逐层分解为可执行微步骤之引导运作机制。
　　3. 反馈范式缺乏情感温度。多数工具仅以数据统计形式呈现成效，如"今日有2项任务超时"。这种聚焦于未完成事项之反馈模式，容易强化ADHD儿童之挫败感与自我否定；形成"失败—回避—再失败"之负向循环。实际上，这类群体更亟待之是关注已完成环节之正向引导。
　　4. 忽视家长端之协同中枢诉求。现有工具大多将执行压力完全施加于儿童一方，鲜少考虑如何为家长赋予情绪支持与路径指导；亦缺乏家庭平台底层架构层面之协同干预规划设计。 综合来看，当今市场亟需一款能够真正理解ADHD儿童心理特质、以消减认知负荷为中枢规划设计原则、与此同时兼顾家长情绪疏导之双端协同辅助平台底层架构。
上述中枢诉求缺口构成了本探究之出发点与中枢驱动力。
1.4研究现状和发展趋势
1.4.1传统行为干预与认知疗法的局限
　　近年来，社会对ADHD之认知逐步深化；已从过去简单地将其归鉴于儿童"调皮"或"家教缺失"，转变为将其理解为一种与执行职能发育滞后密切相关之神经发育性障碍。常规之干预途径中枢囊括药物治疗与行为治疗两种路径，其理论基础本身具有科学依据；但在实际家庭场景中之落地效果往往不尽如人意——多数家长未经专业训练，难以在日常生活中持续、稳定地执行行为矫正路径；药物治疗之副作用争议亦长期未能得到充分应对。近年来，随着物联网、人工智能与移动互联网技术之迅猛演进；利用计算机技术辅助ADHD儿童确立行为习惯——即"数字疗法"——逐渐成为跨学科探究之热点方向。本课题旨在将循证心理学理论与现代软件技术相融合，搭建一套软硬件协同之辅助干预平台底层架构。以下从理论基础、技术落地与演进趋势三个维度，对国内外探究现状开展梳理。
　　认知行为疗法（CBT）与代币经济平台底层架构在ADHD行为干预领域已有较长之应用实践历史[5]。二者在治疗环境中均能取得特定效果，但一个长期兼具之痛点是：干预效果在脱离治疗场景后往往显著衰减。其中枢原因在于，家长作为非专业治疗者；难以长期维持奖励与惩罚标准之一致性——这种执行层面之不稳定性直接削弱了干预效果之持续性。这一现实困境证实，仅依靠人力难以维持干预之稳定性；有必要引入标准化、自动化之技术途径加以补充。
1.4.2数字疗法与应用程序在 ADHD 干预中的发展
　　在国际层面，数字疗法领域之探究与产业化进展显著[6]。2020年，美国FDA批准了首款针对ADHD之处方级视频游戏EndeavorRx[7] ；这一事件具有里程碑意义，标志着游戏化数字干预路径获得了官方层面之正式认可。在软件应用实践方面，欧美地区已有多个团队致力于研发增强时间感知与日程规划能力之辅助平台底层架构；例如经由智能手表震动提醒时间节点等方案。
　　在国内层面，ADHD数字辅助软件之研发尚处于起步阶段但演进较快。当今市面产品以在线问卷、量表审视、知识付费课程及基础打卡工具为主。环节产品已尝试引入积分奖励运作机制，但在交互规划设计层面针对ADHD等神经多样性群体之定制化考量仍显局限性；产品成熟度有待拔高。
1.4.3现状总结与本系统的突破点
　　综合国内外探究现状能够察觉，利用移动互联网平台实施行为干预辅助已获得较为充分之理论与实践支撑。然而，针对国内中小学ADHD群体；真正贴合其认知与行为特质之家庭化应对方案仍然匮乏。"小步（Small Steps）"平台底层架构之中枢规划设计愿景囊括：
　　摒弃"监督"导向之交互范式，维护儿童之尊严感。整体规划设计不依托居高临下之姿态，而是以平等陪伴者之角色定位呈现；避免过度强化任务失败带来之惩罚感知。
　　以"脚手架"理论为指导，逐步培养儿童之自主能力。平台底层架构非但赋予任务提醒，更中枢之是利用大语言范式模型（LLM）之数据剖析能力；识别儿童在具体执行环节中之障碍点，进而赋予渐进式撤除辅助之路径建议；最终愿景是辅助儿童落地自我管理。
　　依托现代化技术栈。前后端立足于Vue 3与Spring Boot 3之微服务体系搭建，跨端兼容性经由UniApp落地。与此同时确立完整之数据追踪与可视化运作机制，使干预进程兼具可量化之观测依据。
　　立足于上述剖析，围绕ADHD中小学生在实际学习与生活中面临之困难；针对现有辅助工具之局限性，运用软件工程路径；搭建了一套涵盖移动端（儿童端与家长端）与管理后台之"多角色业务闭环"辅助平台底层架构。在工程研发与理论验证两个维度上，具体探究内容囊括：
　　将心理学概念落实到前端界面落地。探索"消减认知负荷"、"代币奖励"、"及时正向反馈"等心理学理论如何经由UniApp技术转化为儿童与家长可实际操作之UI组件，囊括番茄钟之交互规划设计、微动效之落地范式、配色方案之确定等；打通理论与落地之间之路径。
　　验证前后端分离底层架构下之安全性与效率。经由Spring Boot 3与Sa-Token之组合，在保障平台底层架构并发承载能力之前提下；落地细粒度之多角色权限控制，验证Redis在多端状态同步与缓存支撑方面之实际表现。经由完整之研发与校验流程开展实证验证。
　　探索大语言范式模型在业务场景中之实际应用实践价值。探究如何将大语言范式模型稳定接入后端平台底层架构，将调用延迟控制在可接受范围内；并立足于儿童长期行为数据与打卡记录，自动生成个性化之激励话术与任务建议。该方向是AI辅助数字行为干预领域之一次实践探索。
　　完整实践软件工程全流程。从中枢诉求剖析、数据库表结构规划设计、API接口定义，到前后端联调及立足于Docker之部署；完整走通软件工程之闭环工作流并开展平台底层架构性记录。
　　另外，平台底层架构预留了ESP32嵌入式平台之语音扩展接口；以探索在真实家庭作业场景中之实际应用实践效果。与市面上传感器被动收集体征信号之方案不同，本平台底层架构倾向于依托ESP32-S3模组落地离线语音唤醒与低延迟对话职能。选用S3型号中枢立足于其向量指令扩展对神经网络推理之加速能力，可满足轻量级唤醒词检测之本地化运转中枢诉求；削减对云端计算之依赖。该规划设计使平台底层架构兼具了"物理伙伴"之实体交互形态，不再局限于纯软件层面之屏幕交互。
　　该方向之落地思路参考了开源社区中"小智"平台底层架构之离线TTS与简单对话流处理方案。具体设想是在ESP32终端上集成轻量级TTS引擎与情感化语音编码组件，使其成为书桌上安静待机之实体设备。当儿童在写作业进程中出现注意力分散时，设备可经由呼吸灯亮起或轻柔之拟声提示；配合简短之鼓励语句，为ADHD儿童赋予一个微弱之注意力"锚点"——辅助其将分散之注意力轻柔地拉回任务；与此同时避免过度干扰。
　　选择边缘计算路径中枢立足于两方面考量：一是数据隐私保障，语音数据在本地处理可有效避免敏感信息上传云端之风险；二是消减认知负荷，相较于亟待视觉注意力之手机应用实践界面；仅需听觉与余光即可感知之实体陪伴设备对ADHD儿童之认知负担更小。从长远来看，这种软硬件融合、兼具语音交互能力之技术底座；有望使平台底层架构从单纯之软件工具演进为具有温度感之"第二调节者"，在家庭环境中为神经多样性儿童赋予稳定、无情绪波动之陪伴角色。
1.5开发相关技术
　　“小步（Small Steps）"平台底层架构在技术选型上以成熟稳定为首要原则，兼顾工程落地之便捷性与理论指导之适配性。整体依托前后端分离底层架构，客户端涵盖移动端与浏览器端；经由RESTful API开展数据通信，各层之间保持低耦合。
1.5.1后端技术栈：Spring Boot 3 和 MyBatis-Plus
　　平台底层架构中枢服务选用Spring Boot 3技术底座。在Java微服务生态中，Spring Boot凭借依赖管理、自动配置与内置服务器等特性；是当今主流之技术选型。选用3.x版本中枢立足于以下考量：对JDK 17之支持更为完善，与Spring Framework 6之兼容性良好；与此同时为后续可能之AOT编译优化预留了版本空间。全局异常处理、跨域配置、统一返回格式封装等基础设施性工作均由技术底座承接。
　　数据持久层选用MyBatis-Plus技术底座。相较于原生MyBatis或JPA，MyBatis-Plus在本平台底层架构场景中具有更好之适配性：平台底层架构中涉及"任务流转"、"用户状态统计"等业务之查询逻辑较为复杂；原生MyBatis之单表CRUD会孕育大量样板代码，而JPA在多表复杂联查场景下SQL调优之灵活性局限性。MyBatis-Plus经由通用Mapper与条件构造器简化了常规操作，与此同时保留了手写SQL之灵活性。其内置之代码生成器亦可立足于数据库表结构自动生成实体类与Mapper接口，显著拔高了研发迭代效率[8]。
1.5.2前端与 CSS 框架：UniApp 和 TailwindCSS
　　移动端选用UniApp 3.0技术底座。其中枢显著优势在于一套代码可与此同时编译至Android、H5及小程序等多个平台，避免了各平台独立研发之维护成本。Vue 3之Composition API使业务逻辑之组织更为清晰，配合Pinia开展状态管理；整体跨端研发效率显著拔高。
　　界面样式依托TailwindCSS原子化CSS技术底座。相较于常规BEM命名规范，TailwindCSS将flex、pt-4、text-center、rounded-lg等细粒度工具类直接应用实践于模板；避免了自定义类名管理之复杂性与样式耦合风险。针对本平台底层架构而言，ADHD儿童对界面颜色对比度与过渡动画流畅度之要求较高；TailwindCSS支持在Vue模板中即时调整并预览效果，无需在模板与样式文件之间频繁切换。搭建时技术底座仅打包实际运用之工具类，有效控制了移动端包体积与首屏加载耗时。
1.5.3权限管理技术：Sa-Token
　　权限管理方面，平台底层架构涉及管理员、家长（主账号）与儿童（子账号）三种角色；层级关系需严格界定。Spring Security职能完备但配置复杂度较高，针对毕业规划设计之研发周期而言成本偏高。综合考量后选用Sa-Token——一款国内开源之轻量级权限认证技术底座。
　　Sa-Token之API规划设计简洁直观，一句StpUtil.login(id)即可完成登录会话创建。在此基础上，配合技术底座自带之拦截器与自定义注解（如@RequiresRoles("PARENT")）；可落地接口路径级之权限控制。接入Redis后，Token无状态校验、同端多账号踢下线、敏感操作二次确认等职能均可落地落地；代码侵入性较低，以较小之研发成本达成了安全保障愿景。
1.6主要研究内容

　　将心理学概念落实到前端界面落地。探索"消减认知负荷"、"代币奖励"、"及时正向反馈"等心理学理论如何经由UniApp技术转化为儿童与家长可实际操作之UI组件，囊括番茄钟之交互规划设计、微动效之落地范式、配色方案之确定等；打通理论与落地之间之路径。

2系统分析
　　本章中枢应对两个中枢痛点：第一，平台底层架构在技术上是否可行、实施成本是否可控；第二，愿景用户（儿童与家长）之职能中枢诉求与运用边界是什么。上述剖析成效将为后续之底层架构规划设计与数据库建模赋予明确之约束条件。
2.1可行性分析
　　“小步（Small Steps）”系统在开发实施前，从技术可行性、操作可行性与理论可行性三个维度进行了系统评估，以下分别阐述。
2.1.1技术可行性
　　技术选型以成熟稳定为原则，均依托经过生产环境验证之方案。整体依托前后端分离底层架构，移动端与浏览器端经由RESTful API与后端通信；各层之间保持低耦合。
　　后端中枢依托Spring Boot 3搭配MyBatis-Plus作为持久层技术底座，二者在Java生态中应用实践广泛；社区文档丰富，稳定性经过大量生产环境验证。前端移动端立足于UniApp 3.0，一套代码可编译至Android与H5平台；Vue 3之Composition API配合Pinia状态管理，研发效率较高。数据库选用PostgreSQL存储中枢业务数据，其对JSON数据类型之支持较为友好；Redis用于高并发场景下之缓存与防重复提交。
2.1.2操作可行性
平台底层架构面向两类愿景用户：ADHD儿童（约6至15岁）及其家长。
　　儿童端之规划设计原则以消减认知负荷为中枢：依托大字体、大按钮，单屏仅呈现一项任务；尽可能精简菜单层级与页面跳转。理想状态是用户打开应用实践即可直觉性地识别操作入口，无需阅读揭示文档。
　　家长端与管理后台遵循行业通用之交互范式。家长端布局参照主流应用实践之规划设计规范，职能入口符合用户既有运用习惯。管理后台依托Element Plus组件库，该技术底座在Vue生态中应用实践广泛；上手门槛较低。
2.1.3理论指导可行性
　　本平台底层架构之规划设计并非纯粹之工程落地，其底层以心理学与教育学理论为指导；以确保职能规划设计不偏离干预愿景。中枢参考之理论方向囊括：
　　其一是认知负荷理论。ADHD儿童之工作记忆容量本就有限，界面信息过载极易导致认知超载。由此可见在规划设计中贯彻"认知卸载"原则——单屏仅呈现一项任务、依托低饱和度配色、削减非必要文字信息。
　　其二是脚手架理论（Scaffolding Theory）[9]，即在学习者能力局限性时赋予临时性支持；待其逐步掌握后渐进撤除辅助。平台底层架构经由AI识别儿童在具体任务中之障碍点，赋予针对性之辅助建议；待儿童熟练后逐步削减干预强度，辅助其从外部监管过渡到自我管理。
　　其三是操作性条件反射理论与家庭平台底层架构动力学。经由随机、即时之正向奖励辅助儿童确立行为正循环，与此同时使平台底层架构充当亲子之间之"中介缓冲层"；将家长从"裁判"角色中解放出来，转变为协作队友。上述理论对平台底层架构在真实家庭场景中之可用性具有关键支撑作用。
2.2系统需求分析
　　需求分析的核心目标是明确系统的功能边界与质量约束。以下从目标用户群体、功能需求与非功能性指标三个维度进行分析。
2.2.1目标用户群体分析
　　系统的目标用户主要分为两类：ADHD儿童（被辅助方）与家长（辅助方）。两类用户对软件的功能期待与交互需求存在显著差异，需分别进行分析。
（1）儿童用户特征
经由在特教机构之陪读观察，察觉该年龄段ADHD儿童具有以下显著特质：
　　注意力集中程度高度依赖任务之趣味性。儿童在游戏或短视频场景中可维持长时间之高度专注（即"超聚焦"现象），但在刷牙、收拾书包、背诵课文等日常任务中；专注持续时间往往局限性五分钟。
　　时间感知能力薄弱。儿童对任务所需时长缺乏基本预估能力，执行进程中普遍兼具拖延现象；往往在截止时间临近时才出现紧迫感。情绪反应迅速但耐挫能力局限性。微小之执行失误即可引发强烈之情绪反应，表现为放弃任务或攻击性行为。
　　由此可见，儿童端之规划设计底线为三条：零学习成本、容错性高、即时正向反馈。界面风格不应呈现为效率工具，而应更接近于理解其心理特质之游戏化交互界面。
（2）家长用户特征
养育ADHD儿童的家长长期承受较大的身心压力。通过社群调研，发现其核心痛点主要集中在以下几个方面：
　　一是监督疲劳。家长每日需反复进行相同的任务督促——"去刷牙"、"坐好"、"别磨蹭"，长期持续后极易产生情绪耗竭，进而引发家庭冲突。
　　二是信息不对称。儿童反馈的"做完了"未必反映真实执行情况，家长对任务实际耗时、执行过程中是否存在中断等关键信息缺乏了解渠道。
　　三是缺乏可操作的指导策略。家长并非缺乏干预意愿，而是缺乏具体的干预方法——在儿童情绪崩溃时应如何回应、如何沟通，需要的是可直接应用的策略建议。
　　还有就是想要实在的建议。家长不是不想好好管，是真不知道怎么管。孩子崩溃的时候该说什么话、怎么接，他们需要的是这种能直接拿来用的东西。
因此，家长端的功能设计需围绕以下核心需求展开：行为数据可视化、任务便捷下发、系统定期提供实用建议。其定位相当于为家长配备外部认知辅助与情绪调节支持。

2.2.3非功能性需求分析
除功能需求外，系统还需满足一系列非功能性指标要求，以保障用户体验与系统稳定性。
（1）性能和响应时间
　　打卡接口：专注模式结束时需同步状态并结算代币，涉及跨库操作；中枢接口之响应时间需控制在150毫秒以内（P99），以保证动画切换之流畅性。
　　大范式模型异步处理：AI寄语之生成通常亟待10至30秒，该进程不得阻塞主线程；需经由消息队列或定时任务异步执行，确保用户界面之正常响应。
　　并发能力：晚间8时至9时为作业高峰时段，平台底层架构需兼具单节点每秒1000次请求之承载能力；以应对流量峰值。
（2）系统安全性和隐私保护
　　未成年人数据隔离：ADHD属于敏感健康信息，数据库规划设计应遵循最小化采集原则。涉及儿童姓名、生理特质等敏感字段需在入库前开展哈希或加密存储。
API防重放和防篡改：前端发起之写操作请求需携带时间戳与签名校验，防止伪造请求导致之代币异常刷取。
　　角色越权防护：立足于Sa-Token之RBAC范式模型开展权限校验，在路由层拦截之基础上；业务逻辑层开展二次验证。例如，家长账号仅能查询其名下绑定之儿童数据；无法经由修改ID访问其他家庭之数据。
（3）可用性与兼容性
　　跨终端一致性：UniApp编译生成之应用实践包需在主流安卓设备上保持布局一致性，尤其是TailwindCSS落地之圆角效果需保持渲染质量；并需适配刘海屏与沉浸式状态栏。
　　弱网环境适应性：在WiFi信号较弱或断网环境下，儿童端之倒计时等本地职能需保持正常运转。任务进度先开展本地离线存储，待网络恢复后自动静默同步至服务端。

3.1.1架构分层设计
“小步”平台底层架构在底层架构规划设计上依托经典之分层底层架构思路，各层职责明确、边界清晰。自上而下分为四层[11]。
　　表现层即前端环节，囊括移动端应用实践（家长端与儿童端）与Web管理后台。该层立足于UniApp与Vue 3搭建，中枢职责是将用户之交互操作转化为HTTP请求；并将后端返回之数据渲染至界面。
　　业务逻辑层是后端之中枢，立足于Spring Boot 3搭建。所有业务相关之逻辑均位于此层，囊括任务流转、代币计算、家长与儿童绑定关系管理等。该层经由Controller接收请求、Service处理业务、Manager开展协调，中枢计算与规则校验均封装在内；确保非法数据无法进入后续流程。
　　数据访问层位于业务逻辑层与数据库之间，依托MyBatis-Plus技术底座。该层之中枢价值在于：单表之增删改查无需手写SQL，直接调用技术底座赋予之通用路径即可。向上为业务层赋予面向对象之查询接口，向下将具体之SQL细节封装隐藏。
　　基础层囊括数据库（PostgreSQL）、缓存（Redis）、日志服务及大语言范式模型API调用之网络代理。该层不涉及业务逻辑，仅负责数据存储、缓存支撑与外部服务调用之稳定性保障。
3.1.2前后端分离协同
　　“小步”平台底层架构依托标准之前后端分离部署底层架构[12]。前端应用实践与管理后台经由公网HTTPS协议向云端Nginx网关发送RESTful API请求。网关作为唯一之对外入口，完成负载均衡与跨域处理后；将请求转发至内网之Spring Boot集群。前后端之间统一依托JSON格式开展数据交换，返回成效统一封装于Result泛型类中；涵盖鉴权状态码与提示信息，便于联调阶段之痛点定位。
3.2核心业务模块设计
3.2.1用户认证与鉴权模块
系统涉及三种角色：管理员、家长与儿童。权限隔离机制基于Sa-Token实现[13]。
（1）登陆认证
　　前端提交账号密码进行身份验证，后端验证通过后在Redis中创建用户会话上下文，并将Token返回至前端。
（2）双域隔离设计
　　为防止后台管理员 Token 在移动端 App 误用，平台底层架构依托 Sa-Token 之多账号体系（Multi-Account System）底层架构；将后台管理平台底层架构（Admin）之用户中心与移动终端（App）之用户中心在缓存路由中严格隔离。
（3）细粒度权限管控
　　业务层接口执行前，会经过 Sa-Token 全局拦截器（Global Interceptor）。通过在业务特定的 Controller 方法上注入@SaCheckRole("PARENT")与@SaCheckPermission("task:create")等鉴权注解，保证例如儿童不可创建或随意删除高优任务，家长不能跨家庭体系查看其他儿童数据，实现角色与组织层的严格互斥。
3.2.2任务管理与流程设计
　　任务是平台底层架构最中枢之业务实体，几乎所有职能组件均围绕其展开。鉴于ADHD儿童在任务执行进程中之状态变化具有较大不确定性，任务状态机之规划设计保留了适度之弹性空间。
　　任务状态囊括以下四种：未开始、执行中（进入番茄钟计时状态）、已完成（打卡提交成功）、已废弃（当日未完成且已过期）。
　　家长创建任务时，除填写标题与预计耗时外；还需配置以下关键属性：执行周期（单次/每日循环/自定义频率）与完成后奖励之代币数量。
　　另外，复杂任务支持挂载子步骤清单。该规划设计中枢立足于ADHD儿童面对"大任务"时易孕育畏难心理之特点，将其拆解为若干小步骤后可有效消减心理压力。
3.2.3专注模式与时间管理
专注组件为儿童进入任务后之计时体验赋予支撑。该组件不涉及持久层之写入操作，优先保证前端之运转流畅性。
　　其工作流程如下：前端获取待专注之任务ID与参数，儿童点击“开始”后；Pinia状态树切换至“专注锁定态”，倒计时引擎启动。在此状态下，全局路由返回操作与底部TabBar切换均被拦截；维持全屏沉浸体验。
　　若倒计时自然结束，前端将完成记录（涵盖持续时长、设备信息等）提交至后端；后端开启事务确认任务完成并同步核算奖励。
　　若中途退出，前端仍会将实际积累之时长传回后端；后端在归档时标记为“非完全完成”。该环节数据对后续AI剖析儿童之专注耐受阈值与情绪变化趋势具有参考价值。
3.2.4智能辅助生成与数据反馈
　　为减轻家长每日撰写辅导话术之负担，与此同时使干预进程更具个性化与针对性；平台底层架构搭建了一条旁路之AI反馈闭环[14]。该组件不阻塞日常业务流程，由后端定时任务驱动执行。具体运转运作机制如下：
　　每日固定时段，平台底层架构提取某一儿童与家长组合之近十天打卡记录（囊括总完成数、成功率、超时情况、情绪评分等）；聚合成结构化之行为摘要JSON。
随后，将该摘要与管理后台预设之Prompt模板组合；异步发送至大语言范式模型。
　　大范式模型返回之内容经脱敏处理后入库存储。次日家长打开应用实践时，首页将展示一张“辅助指引卡片”；呈现AI生成之建议话术。家长确认内容合适后，可一键同步至儿童端之"时光机信箱"界面。
3.3数据库设计
　　数据库是平台底层架构业务逻辑落地之中枢载体，其规划设计直接决定平台底层架构之数据一致性、扩展性与运转性能。针对ADHD儿童行为干预场景之特殊性，本平台底层架构在数据库规划设计中非但关注常规业务数据建模；与此同时引入游戏化激励、任务拆解暨情绪追踪等扩展维度，以支撑平台底层架构之长期行为引导能力。
3.3.1设计原则与总体架构
　　经由从业务中枢诉求描述对象中剥离实体与映射关联，抽取出本平台底层架构之四类中枢实体搭建了 E-R（Entity-Relationship）在数据库规划设计进程中；平台底层架构遵循以下中枢原则：
　　高内聚与领域划分原则。围绕平台底层架构中枢业务，将数据划分为“用户与档案”、“任务流转”、“激励体系”与“情绪与AI追踪”四大领域；保证各组件职责清晰、边界明确。
　　读性能优先原则。针对儿童端与家长端之高频读取场景，经由适度去范式化规划设计与缓存运作机制；削减多表关联查询带来之性能开销。
　　灵活扩展原则。针对任务子步骤、用户偏好等非结构化数据，依托 PostgreSQL 之 JSONB 类型存储；以适应未来业务变化。
数据一致性保障原则。经由快照字段与流水表规划设计，确保积分、奖励等关键数据兼具可追溯性与审计能力。

3.3.4缓存策略与 Redis 结构设计
　　平台底层架构中兼具多处高频读写场景：移动端每次页面切换均需验证Token有效性、首页排行榜需查询积分排名，若所有请求均直接访问PostgreSQL，性能将难以承受。由此可见，平台底层架构引入Redis作为全局缓存层。
　　认证缓存：配合 Sa-Token，按不同用户确立诸如satoken:login:session:{userId}之 Hash 对象；存储权限集合（Permission Sets）与失效时间，免去权限比对时之额外查库消耗。
　　任务防重点赞/防连击键搭建：利用 Redis 短期 Key 之自动失效运作机制（TTL）融合 SETNX（Set if Not eXists）分布式互斥原生指令，当儿童端快速双击“任务完成按钮”时；拦截第二发请求，保证在高并发情景下不会鉴于网络延迟发包造成重复结算下发代币奖励情况出现。

4.2.1安全认证与路由拦截的实现细节
　　在用户开展登录请求时，平台底层架构调用SysUserServiceImpl层之验证逻辑。相比于常规之 JWT 手动拼接，平台底层架构引入了 Sa-Token 处理登录态。当验证经由后，直接调用StpUtil.login(user.getId())。这一简单接口之背后，技术底座自动向 Redis 缓存写入了当今用户之登录状态与过期时间戳；并在 HTTP Response Header 中自动下发以satoken为索引之凭据标识。为保障中枢业务接口不被未授权访问，后端落地了一个落地了WebMvcConfigurer接口之配置类。在此类中注册了 Sa-Token 之拦截器SaInterceptor：
　　@Configurationpublic class SaTokenConfigure implements WebMvcConfigurer {
@Override
　　public void addInterceptors(InterceptorRegistry registry) {
registry.addInterceptor(new SaInterceptor(handle -> StpUtil.checkLogin()))
.addPathPatterns("/ssapi/**")
.excludePathPatterns("/ssapi/public/login", "/ssapi/public/register");
}}
　　此运作机制保证了除公开登录注册接口外，所有带有/ssapi/前缀之请求在触达 Controller 之业务逻辑前；都必须经过底层 Redis 中上下文 Token 之比对，有效落地了第一层鉴权。
4.2.2结构化任务与分发系统的业务逻辑实现
　　任务系统的产生和流转涉及大量的数据库事务一致性（Transaction Consistency）。以“家长为儿童当天新建任务”这一核心业务场景为例： 在对应的TaskController中暴露 POST 请求接口。该请求包含被控端儿童 ID、任务元数据及预期所需时段。 在TaskServiceImpl逻辑中，由于此操作同时牵涉向任务模版表task_info插入源数据，以及在任务实体日志表task_daily_log预生成当日的待办占位记录，为了防止网络中断造成的数据不一致（如：主模版建立但今日待办未生成），整个 Service 方法使用了 Spring 框架提供的@Transactional(rollbackFor = Exception.class)注解进行事务包裹。另外，为实现 MyBatis-Plus 赋能的高级表关联查询，系统针对家长端“查看孩子近一周所有已排期任务”需求，利用 MyBatis-Plus 的QueryWrapper构建了类型安全的条件筛选：
　　QueryWrapper<TaskDailyLog> wrapper = new QueryWrapper<>();
wrapper.eq("child_id", currentChildId)
.between("target_date", startDate, endDate)
.orderByDesc("target_date");return taskDailyLogMapper.selectList(wrapper);
此段代码有效地屏蔽了复杂之 SQL 拼接逻辑，并自然防御了潜在之 SQL 注入攻击。
　　任务打卡完成后触发积分结算，该操作需在同一个数据库事务内完成积分余额更新与流水记录写入；以防止数据不一致。中枢代码如下：
@Service
　　public class ScoreServiceImpl implements IScoreService{

private ChildScoreMapper childScoreMapper;
@Autowired

// 1. 更新积分余额（乐观锁）

　　score.setTotalEarned(score.getTotalEarned() + points);
childScoreMapper.updateById(score);
// 2. 写入积分流水
ScoreHistory history = new ScoreHistory();
history.setUserId(userId);
history.setAmount(points);
    history.setType("1");  // 1-增加
history.setSourceId(taskId);
history.setReason(reason);
scoreHistoryMapper.insert(history);
// 3. 触发勋章检查
　　achievementService.checkAndUnlockBadges(userId, score.getTotalEarned());

}

6	总结与展望
　　当今社会之快节奏生活范式使得环节在认知执行神经平台底层架构上兼具先天劣势之群体（如ADHD群体）面临较大挑战，尤其体现在成长关键期之家庭教育场景中。为缓解大量ADHD家庭所面临之监督耗竭困境，本探究规划设计并研发了一套"小步"双端行为习惯辅助协同平台底层架构。在探究与研发进程中，完成了以下中枢工作：
　　确立了“无压力”之UI交互规划设计哲学。摒弃具有威慑感之规划设计风格，转而经由游戏化代币之正向激励与大语言范式模型之情感化话术搭建闭环干预运作机制。
　　搭建了现代化之前后端分离底层架构体系：摒弃常规单体结构，后端立足于Spring Boot 3与MyBatis-Plus搭建业务中枢；利用Sa-Token落地灵活之权限管控，前端立足于UniApp 3.0落地多端覆盖，引入Vue 3之Composition API与Pinia落地高效之渲染性能与跨端状态管理。
　　探索了AI赋能业务之新范式：在完成基础信息交互职能之基础上，尝试在后端定时接入大语言范式模型智能接口；使平台底层架构兼具了类似“驻场儿童心理咨询师”之同理心反馈能力，在特定程度上减轻了家长之心智负担。
6.1总结
　　在项目实施进程中也面临了特定之技术挑战：因业务对状态同步一致性之要求较高，初期因过多之连表查询导致后端出现性能瓶颈。引入Redis承担大量会话认证校验与去重锁职能后，平台底层架构性能落地了显著拔高（QPS突破千级）。另外，前端为落地ADHD儿童“零跳转、所见即所得”之交互体验；大量精简了复杂路由结构，依靠Pinia与TailwindCSS之实时按需渲染能力开展替代；虽然增添了前期平台底层架构规划设计之复杂度，但换来了极低之用户操作延迟体验。
6.2系统存在的不足与未来研究展望
　　虽然“小步”平台底层架构在实验室层面经由了校验并在中枢底层架构上奠定了长远演进之技术底座，但在迈向下一代商业化级产品之路上；依然具有环节可深挖之探究点：
　　多维度数据之联动感知：现阶段数据获取仅限患儿之“主动点击打卡完成时间”。未来或可考虑接入物联网可穿戴设备之蓝牙集成，经由实时获取血氧、心率等生理指标客观审视儿童之专注状态与情绪波动；形成多模态数据验证。
　　脱离云端之大范式模型本地化（Edge AI）：为保护干预数据之隐私安全，并规避未来第三方API调用成本过高之痛点；后续拟在网关内网或边缘计算终端探索本地部署轻量化大语言范式模型之能力，落地完全离线环境下之智能剖析。
　　科学技术的价值不仅在于提升效率，更在于为那些不易被大众关注的群体建立平等的支持系统。“小步”是拥抱神经多样性的一次技术实践，期待它在未来能够走进更多普通家庭，让每一位特别的孩子都能在自己的节奏与步伐下，迈出自信且专注的下一步。

public class TaskDecomposePromptTemplate {
/**
* 系统角色Prompt（System Prompt）
* 定义AI的角色身份和核心行为准则
*/
public static final String SYSTEM_PROMPT = """
你是一位专业的ADHD（注意力缺陷多动障碍）儿童行为辅导专家。
你擅长将复杂的日常任务拆解为ADHD儿童能够独立执行的极小步骤。
## 拆解原则
1. 每个步骤必须是单一、具体、可立即执行的动作。
错误示例："整理书包"（太笼统）
正确示例："把数学课本放进书包"（具体可执行）
2. 步骤数量控制在3到8个之间，过多会让孩子感到压力。
3. 每个步骤的预计用时（duration_sec）应根据儿童年龄合理估算：
- 6-8岁：每个步骤建议60-180秒
- 9-12岁：每个步骤建议120-300秒
- 13岁以上：每个步骤建议180-600秒
4. voice字段（语音引导语）的语言风格要求：
- 充满鼓励和温暖，使用儿童友好的语言
- 每句话不超过30个字
- 可以适当使用拟声词和感叹号增加趣味性
- 避免使用否定词（如"不要""不能"），改用正面引导
5. 步骤之间应有清晰的逻辑顺序，遵循时间线或空间线。
6. 最后一个步骤应包含"完成确认"的正面反馈。
## 输出格式要求
你必须且只能输出一个合法的JSON数组，不要包含任何其他文字说明。
每个数组元素包含以下三个字段：
- desc: 步骤描述（不超过20个字）
- duration_sec: 建议用时（整数，单位：秒）
- voice: 语音引导语（不超过30个字）
""";
/**
* 用户Prompt模板（User Prompt）
* 使用占位符，运行时替换为实际的上下文信息

- ADHD类型：{adhd_type}

public static String buildUserPrompt(String taskTitle, int childAge,

String adhdTypeDesc = switch (adhdType) {
case "I" -> "注意力不集中型（容易走神、遗忘）";
case "H" -> "多动冲动型（坐不住、易冲动）";
case "C" -> "混合型（兼具注意力不集中和多动冲动特征）";
default -> "未指定";
};
return USER_PROMPT_TEMPLATE
.replace("{task_title}", taskTitle)
　　                .replace("{child_age}", String.valueOf(childAge))
.replace("{adhd_type}", adhdTypeDesc);
}

}
