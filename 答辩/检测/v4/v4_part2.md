1.4 研究现状与发展趋势

1.4.1 传统行为干预的局限性

认知行为疗法（CBT）与代币经济系统是目前实证依据最充分的非药物干预手段之一，在正式的治疗环境中均能取得可观效果[5]。但问题在于这个"治疗环境"本身——当儿童离开诊室回到家庭日常后，干预效果往往显著衰退。根本原因是家长作为执行方，很难长期维持奖惩标准的一致性。专业治疗师能做到的事，让一个本身也承受生活压力的普通家长在每天接送上学、做饭辅导的间隙里稳定复现，几乎是强人所难。这种执行层面的不稳定，才是干预效果打折扣的主因，而不是方法本身的理论缺陷。

这一现实困境指向一个具体的需求：需要某种标准化、低人力成本的工具来承担部分执行功能，让家长不必时刻扮演"专业治疗师"的角色。

1.4.2 数字疗法的兴起与现有软件的问题

数字疗法（Digital Therapeutics，DTx）这个概念近年来在学术界和产业界的讨论热度都在上升。一个标志性事件是2020年美国FDA批准了首款针对ADHD的处方级视频游戏EndeavorRx[7]，意味着游戏化数字干预路径在医疗层面获得了官方认可。欧美地区此后也有多个团队在时间感知辅助、日程规划等方向上持续推进相关研究，典型方案如智能手表结合震动提醒来帮助儿童建立时间锚点[6]。

国内的情况则相对滞后。笔者在需求调研阶段浏览了应用商店中几十款宣称面向ADHD或专注力训练的产品，发现多数停留在在线量表评估、付费课程推送或基础打卡记录层面，积分奖励机制也有少数产品引入，但针对ADHD儿童"执行功能障碍"这一核心特征的交互设计几乎付之阙如——界面信息密度高、操作层级深、缺乏即时正向反馈，在实际使用时恰恰会加重这类儿童的认知负担。

1.4.3 本系统的定位与突破点

综合上述背景，笔者将"小步"系统的核心定位明确为：不是又一个通用任务管理工具，而是专门为ADHD儿童的认知与执行特点定制的家庭干预辅助系统。具体的设计目标包括三个层面。

第一，从交互哲学上摒弃"监督"导向。整套系统的角色定位是平等陪伴者而非居高临下的监工，避免用惩罚感知来强化任务失败的心理创伤。

第二，以"脚手架"理论[9]为指导，将辅助强度设计为可逐步撤减的。系统不只是提供任务提醒，更通过大语言模型对儿童行为数据的分析识别具体的执行障碍点，进而提供渐进式减少干预的策略建议——长期目标是帮助儿童实现自我管理，而不是永久依赖工具。

第三，在技术实现上选用经过生产环境验证的成熟方案，确保系统稳定性足以支撑长期使用场景。


1.5 开发相关技术

"小步（Small Steps）"系统在技术选型上遵循的是"够用且稳定"的原则，而不是追求技术栈的新颖性。面向ADHD儿童的系统，如果底层不稳定、接口响应慢或者前端动画卡顿，本身就会破坏用户体验，所以稳定性是首位考量。整体采用前后端分离架构，客户端涵盖移动端与浏览器端，各层通过RESTful API通信，保持低耦合。

1.5.1 后端技术栈：Spring Boot 3 与 MyBatis-Plus

后端框架选用Spring Boot 3。这个选择没有什么特别的创新性，Spring Boot在Java微服务生态里的地位已经相当稳固，依赖管理、自动配置、内置服务器等机制使项目搭建的初期成本很低。选3.x版本主要是两个考虑：一是对JDK 17的支持更完善，与Spring Framework 6兼容性良好；二是为后续可能的AOT编译优化预留了版本空间。全局异常处理、跨域配置、统一响应格式封装这类基础设施工作由框架统一承接，开发中不需要重复造轮子。

持久层的选择上，笔者最初考虑过JPA——配合Hibernate的映射能力，实体类与数据库表之间的绑定相当便利。但实际写到任务流转、用户状态统计这类业务时，多表复杂联查的SQL调优灵活性不够，JPA生成的SQL难以直接优化。最终换成MyBatis-Plus：单表CRUD通过通用Mapper一行代码解决，复杂查询保留手写SQL的能力，两端都照顾到了。其内置的代码生成器能基于数据库表结构直接生成实体类与Mapper接口，在迭代比较频繁的毕设开发节奏下省了不少时间[8]。

1.5.2 前端与 CSS 框架：UniApp 与 TailwindCSS

移动端选用UniApp 3.0。核心原因是跨平台：一套代码可以编译至Android、H5和小程序，在毕设的开发周期内，笔者没有余力分别维护多套代码。Vue 3的Composition API在逻辑组织上比Options API更清晰，配合Pinia做状态管理，整体开发体验较好。

样式方案采用TailwindCSS原子化CSS框架。坦白说，这个选择在项目初期引发过不少争议——有观点认为原子类会让模板代码显得冗长、可读性下降。但实际使用下来，对于本系统的场景有两个实际好处：ADHD儿童界面对颜色对比度和动画流畅度要求较高，TailwindCSS支持在Vue模板中即时调整并预览效果，修改效率明显高于在独立样式文件和模板之间来回切换；另一方面，构建时框架只打包实际用到的工具类，有效控制了移动端包体积。

1.5.3 权限管理：Sa-Token

权限层涉及管理员、家长（主账号）、儿童（子账号）三种角色，层级关系需要严格区隔。最初考虑Spring Security——功能完备，但配置复杂度对于本项目的体量而言明显偏高，花在配置文件上的时间可能超过实际业务开发。

最终选用Sa-Token，这是一款国内开源的轻量级权限认证框架。API设计直观，一句StpUtil.login(id)完成登录会话创建。配合框架自带的拦截器和@RequiresRoles("PARENT")这类注解，接口方法级的权限控制落地成本很低。接入Redis后，Token无状态校验、同端多账号踢下线、敏感操作二次确认等需求都能覆盖，代码侵入性不高。对于毕设规模的项目，这个权衡是合适的——当然如果是生产级系统，Spring Security的配置复杂度在团队规模上去后反而是优势，这里就不展开了。


1.6 主要研究内容

本系统的工程实践围绕以下几个方向展开：

将心理学理论转化为可操作的前端实现。"降低认知负荷""代币奖励""即时正向反馈"这些概念，在教育心理学文献里有充分的理论依据，但如何把它们落地为具体的UI组件——番茄钟的交互逻辑、微动效的实现、配色方案的确定——需要在理论与工程之间反复拉通，这是本研究尝试打通的路径之一。

验证前后端分离架构在本场景下的安全性与性能表现。Spring Boot 3加Sa-Token的组合能否在保证并发能力的同时把多角色权限控制做细？Redis的缓存层在多端状态同步中的实际表现如何？这些通过完整的开发与压测流程进行实证验证。

探索大语言模型在业务场景中的接入方式。研究如何将LLM稳定嵌入后端异步流程，把调用延迟控制在不影响用户体验的范围内，并基于儿童历史行为数据自动生成个性化的激励话术。这个方向的工程难点在于熔断降级和数据脱敏，而非模型能力本身。

完整走通软件工程的闭环流程。从需求分析、数据库表结构设计、API接口定义，到前后端联调与基于Docker的部署，完整记录开发过程，也是本研究的一项基础性工作。

此外，系统预留了ESP32嵌入式平台的语音扩展接口。笔者的设想是在ESP32-S3上集成轻量级TTS引擎，使其成为书桌上的实体陪伴设备——当儿童注意力分散时，设备通过呼吸灯或轻柔提示音提供一个非屏幕的注意力锚点，同时不产生过强的干扰刺激。选用S3型号主要是其向量指令扩展对轻量级神经网络推理有一定加速效果，可以支撑本地唤醒词检测。这一方向参考了开源社区"小智"系统的离线TTS处理思路，目前处于概念验证阶段，未在本文核心测试范围内展开。边缘计算路径的两个主要考量：语音数据本地处理规避了敏感信息上传云端的隐私风险；对于ADHD儿童而言，不需要视觉注意力的实体提示设备，认知负担明显低于需要解锁手机看屏幕的应用交互。


1.7 各章主要内容

第2章进行可行性分析与需求分析，明确系统的功能边界与技术可行性；第3章阐述系统总体架构设计，包括业务模块划分与数据库表结构设计；第4章展示系统实现细节，涵盖后端接口开发、移动端页面构建及Web管理后台实现；第5章描述测试方案，搭建测试环境并对核心业务流程进行验证；第6章总结全文工作并对后续方向进行展望。
