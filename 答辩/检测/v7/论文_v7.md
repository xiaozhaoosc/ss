ADHD中小学生（儿童）行为习惯辅助系统设计与实现
　　摘要：	注意缺陷多动障碍（ADHD）是一类与注意维持、活动控制和冲动抑制密切相关的神经发育性障碍，在中小学阶段容易表现为任务启动困难、作业拖延、情绪波动和亲子冲突等问题。药物治疗和线下行为训练仍是常见干预路径，但前者需要持续医学评估，后者对家长执行一致性和专业资源依赖较强。围绕家庭日常场景中“任务难启动、过程易中断、反馈易负向化”的实际问题，本文设计并实现了“小步（Small Steps）”行为习惯辅助系统。系统采用前后端分离架构，由儿童端、家长端和管理后台共同构成：儿童端负责微任务呈现、专注计时和正向反馈，家长端负责任务配置、点亮确认和数据查看，管理后台负责模板、账号和运行数据管理。工程实现上，后端基于Spring Boot 3与MyBatis-Plus完成业务接口和数据持久化，使用Sa-Token实现多角色鉴权，PostgreSQL与Redis分别承担核心数据存储和缓存去重；移动端基于UniApp、Vue 3和Pinia实现家长/儿童双模式切换。系统还引入大语言模型作为辅助生成模块，根据任务完成、专注时长和情绪记录生成鼓励话术及家长建议，并通过异步处理和兜底文本降低外部接口不稳定对主流程的影响。测试结果表明，系统能够完成任务创建、儿童执行、家长点亮、积分结算和奖励兑换等核心流程，为ADHD儿童家庭中的数字化行为辅助提供了可实现的工程方案。

　　Design and Implementation of ADHD Behavior Support System for Children
　　Abstract:	Attention deficit hyperactivity disorder (ADHD) is a neurodevelopmental condition closely related to sustained attention, activity regulation, and impulse control. In everyday school and family settings, children with ADHD often experience difficulties in task initiation, homework persistence, emotional regulation, and parent-child communication. Medication and offline behavioral training remain important intervention approaches, yet they may require long-term medical supervision or stable parental implementation. In response to practical problems observed in home-based habit training, this thesis designs and implements Small Steps, a behavior-support system for elementary and middle school students with ADHD. The system follows a front-end/back-end separation architecture and consists of a child application, a parent application, and an administrative backend. The child application focuses on micro-task presentation, focus timing, and positive feedback; the parent application supports task configuration, confirmation, reward management, and data review; the administrative backend provides account, template, and operational management. The backend is developed with Spring Boot 3 and MyBatis-Plus, Sa-Token is used for multi-role authentication, and PostgreSQL and Redis are adopted for data persistence, caching, and duplicate-submission control. The mobile side is implemented with UniApp, Vue 3, and Pinia to support role-based interface switching. In addition, a large language model is integrated as an auxiliary generation module. It produces motivational messages and parent-facing suggestions from task, focus, and emotion records through asynchronous processing and fallback texts, so the main task workflow is not blocked by external API instability. Functional and performance tests show that the system can support task creation, child execution, parent confirmation, point settlement, and reward redemption, providing an implementable engineering approach for digital behavior assistance in ADHD-related family scenarios.

1绪论
　　注意力缺陷多动障碍（ADHD）在学龄儿童群体中并不少见，其表现通常不只停留在“坐不住”或“注意力差”这类表层现象上，而是与执行功能、时间感知和情绪调节等能力有关。对于中小学阶段的儿童而言，这些困难会直接进入课堂听讲、家庭作业、生活自理和亲子沟通等具体场景。现有干预方式以药物治疗、家长管理训练和线下行为矫正为主，但不同家庭在专业资源、经济承受能力和长期执行条件上存在差异。与此同时，市面上常见的番茄钟或打卡工具大多面向普通效率管理，并未充分考虑ADHD儿童在任务启动、步骤拆分和正向反馈上的特殊需要。因此，开发一套以家庭日常任务为对象、兼顾儿童体验和家长协同的数字化辅助系统，具有较强的现实针对性。
1.1研究背景
　　注意缺陷多动障碍（Attention Deficit Hyperactivity Disorder，ADHD）的全球学龄儿童检出率通常被估计在5%至7%之间[1]。本研究关注的并不是疾病诊断本身，而是ADHD特征在家庭学习任务中的具体影响：儿童可能知道“应该做什么”，却难以稳定地开始、维持并完成任务。相关研究指出，ADHD儿童的智力水平并不必然受损，但执行功能常受到影响，包括工作记忆、计划组织、抑制控制和情绪调节等方面[2]。这些能力短板会使“写作业”“整理书包”“按时洗漱”等普通任务变成多步骤、高负荷的执行过程。
　　在日常学习与生活中，ADHD儿童的困难往往呈现为连续的小失败：课堂上容易被周围声音或物品吸引，家庭作业开始前需要多次提醒，执行过程中又容易因为步骤不清而停顿。在同伴交往中，冲动插话、打断他人或肢体冲突也可能进一步削弱其社会支持。长期反复受挫后，儿童容易形成“我总是做不好”的自我评价，继而出现低自尊、焦虑或回避行为[3]。因此，本课题将研究重点放在日常任务的辅助执行上，希望通过任务拆分、过程陪伴和正向反馈，降低儿童在家庭场景中的认知负担。
1.2研究目的
　　传统ADHD干预主要包括药物治疗和行为干预。药物治疗可以在一定程度上改善核心症状，但在儿童长期用药场景下，家长通常会关注食欲、睡眠和生长发育等潜在影响。行为干预，尤其是家长管理培训（Parent Management Training），在理论和实践中具有较充分依据，但它要求家长持续、稳定地执行规则、奖励和反馈。现实家庭中，家长本身也受到工作、学业安排和情绪压力影响，很难始终保持同一套干预标准。于是，一些家庭会在“提醒、催促、争执、放弃”的循环中消耗精力，干预目标尚未达成，亲子关系已经明显紧张[4]。
　　在这种背景下，数字化工具的价值不在于替代医学诊疗，而在于把重复提醒、任务记录和部分反馈环节从家长身上分担出来。移动应用具有稳定、可记录、可重复执行的特点，适合作为亲子之间的中介层。一方面，它可以把大任务拆成儿童更容易理解的小步骤，并用即时奖励维持参与感；另一方面，它可以减少家长直接催促的频率，使家长把更多精力放在解释、陪伴和情绪支持上。本文所设计的“小步”系统正是围绕这一思路展开。
1.3研究意义
　　从应用市场来看，日程管理、时间追踪和番茄钟类工具数量较多，但这些工具面向的是一般效率需求，直接迁移到ADHD儿童场景时会暴露出适配不足。结合本系统需求调研和原型测试，主要问题可以概括为以下四点：
　　1. 认知负荷过高。通用效率工具通常强调功能完整性，图表、列表、菜单和多级设置同时出现。对于执行功能已经吃紧的儿童来说，这些信息会抢占工作记忆资源，导致还没有开始任务就产生回避。
　　2. 任务分解粒度不足。ADHD儿童常见困难并非完全不会做任务，而是不知道从哪一步开始。以“写作业”为例，如果系统不能继续拆成“拿出作业本、写日期、完成第一题、休息两分钟”等微步骤，儿童仍然会停留在笼统指令前。
　　3. 反馈方式缺乏情感温度。单纯显示“超时”“未完成”会强化失败感。更合适的方式是先确认已经完成的部分，再提示下一步可执行动作，让反馈成为继续行动的线索，而不是新的压力来源。
　　4. 忽视家长端的协同需求。很多工具只把任务推给儿童，却没有给家长提供配置、观察和策略调整入口。对ADHD家庭而言，家长端不是附属功能，而是维持干预一致性的重要环节。综合来看，本课题的研究意义在于构建一套同时服务儿童执行和家长协同的辅助系统。
上述需求缺口构成了本研究的问题起点，也决定了系统在设计上必须同时关注“低认知负荷”和“家庭协同”两个维度。
1.4研究现状和发展趋势
1.4.1传统行为干预与认知疗法的局限
　　近年来，ADHD逐渐从“调皮”“管教不足”等日常化解释中被区分出来，更多被理解为与执行功能发育相关的神经发育性障碍。药物治疗和行为治疗都有各自的理论基础，但在家庭场景中仍存在落地难点：前者需要医学评估和长期随访，后者依赖家长持续执行。随着移动互联网、物联网和人工智能的发展，数字疗法开始为家庭辅助干预提供新的实现手段。本课题的研究并不试图替代专业治疗，而是把循证心理学中的任务拆分、代币奖励和正向反馈原则转化为可操作的软件流程。
　　认知行为疗法（CBT）和代币经济系统在ADHD行为干预中已有较长应用历史[5]。这类方法的关键并不是一次性的奖励，而是规则清晰、反馈及时并且前后一致。问题在于，治疗室中的规则一旦回到家庭环境，就会受到家长情绪、时间安排和儿童临场状态的影响。由此可见，数字系统可以承担“规则记录器”和“反馈触发器”的角色，把原本高度依赖人工记忆和情绪稳定性的环节转化为更可重复的流程。
1.4.2数字疗法与应用程序在 ADHD 干预中的发展
　　在国际层面，数字疗法已经出现较明确的产业化案例。2020年，美国FDA批准了面向ADHD的处方级视频游戏EndeavorRx[7]，说明游戏化与注意训练结合具有一定研究基础。除游戏外，欧美也有团队尝试利用智能手表、震动提醒和日程可视化增强儿童的时间感知能力。这些案例表明，数字工具可以成为ADHD干预的补充路径，但其有效性仍依赖具体场景、交互设计和持续使用机制。
　　在国内，ADHD相关数字产品仍以科普、问卷评估、课程服务和基础打卡为主。部分产品已经加入积分或排行榜机制，但对神经多样性儿童的交互适配仍较有限。例如，任务是否足够小、反馈是否避免羞辱感、家长是否能获得可执行建议，这些问题在通用工具中并未被充分解决。本系统尝试从家庭作业和日常习惯两个高频场景切入，补足这一空白。
1.4.3现状总结与本系统的突破点
　　综合国内外研究现状可以看出，移动互联网平台用于行为辅助具有一定理论和实践基础，但面向国内中小学ADHD儿童的家庭化工具仍不充分。“小步（Small Steps）”系统的突破点主要体现在以下三个方面：
　　第一，弱化单向监督，保留儿童的主体感。系统在命名、按钮文案和奖励反馈上避免使用惩罚式表达，强调“完成一步”“点亮星星”等正向动作，使儿童感受到任务被拆小后可以被完成。
　　第二，引入脚手架思路，逐步降低外部辅助强度。系统先由家长或模板把任务拆成微步骤，再通过执行记录观察儿童在哪些环节停顿，后续由AI模块生成更具体的提示建议，目标是帮助儿童从外部提醒过渡到自我管理。
　　第三，采用可扩展的工程架构。系统前端使用UniApp和Vue 3支持多端适配，后端使用Spring Boot 3组织业务服务，并通过PostgreSQL、Redis和权限框架支撑任务流转、积分结算和数据追踪。
　　基于上述分析，本文围绕ADHD中小学生在学习和生活中的执行困难，采用软件工程方法完成了移动端与管理后台的协同设计。研究内容不是停留在概念层面，而是落实到界面、接口、数据库和测试流程中，具体包括以下方面：
　　第一，将心理学原则转化为前端交互。围绕降低认知负荷、代币奖励和及时正向反馈，设计任务卡片、专注计时、星星奖励和儿童端低干扰界面，并在UniApp页面中实现相应组件。
　　第二，验证前后端分离架构在多角色场景下的可行性。系统通过Spring Boot 3、Sa-Token和Redis实现登录状态、接口权限和防重复提交控制，并结合测试数据观察其在并发访问下的稳定性。
　　第三，探索大语言模型在家庭辅助场景中的边界。系统将AI模块设计为旁路服务，由后端定时聚合任务和情绪数据，生成家长建议与儿童鼓励文本，同时保留兜底话术，避免外部模型失败影响主业务。
　　第四，完成从需求分析、表结构设计、接口开发、前后端联调到Docker部署和自动化测试的完整工程流程，并对关键实现进行记录，为后续扩展硬件端和更多干预策略提供基础。
　　此外，系统预留ESP32-S3硬件终端扩展方向，用于探索“物理伴侣”形式在家庭作业场景中的作用。与被动采集生理信号的设备不同，本设计更关注低打扰提醒和轻量语音互动，例如本地唤醒、灯环提示和简短鼓励语音。ESP32-S3具备一定本地推理能力，可用于轻量级唤醒词检测，减少语音数据上传云端的需求。
　　硬件端设想参考了开源社区中“小智”系统的离线TTS与简单对话流处理方案。实际使用时，设备可放置在书桌附近，在儿童分心时通过呼吸灯或柔和提示音提供一个低强度注意力锚点。该设计不要求儿童频繁看手机屏幕，而是通过听觉和余光完成提醒，从而减少新的视觉负担。
　　选择边缘计算路径主要基于隐私和认知负荷两方面考虑。语音数据本地处理可以降低敏感信息外传风险；实体设备相比手机应用更不容易引入额外娱乐干扰。长期来看，软硬件结合有助于把系统从单纯的任务管理工具扩展为稳定、低情绪波动的家庭陪伴式辅助设备。
1.5开发相关技术
　　“小步（Small Steps）”系统在技术选型上坚持成熟、可维护和易验证原则。系统采用前后端分离结构，移动端、管理后台和后端服务通过RESTful API交换数据；业务层、持久层和缓存层各自承担明确职责，以降低后续扩展和维护成本。
1.5.1后端技术栈：Spring Boot 3 和 MyBatis-Plus
　　系统核心服务选用Spring Boot 3。该框架在Java后端开发中具有较成熟的依赖管理、自动配置和Web服务能力，适合毕业设计中较复杂的业务模块组织。本项目选择3.x版本，主要是考虑其对较新JDK版本和Spring Framework 6生态的支持，同时便于后续扩展统一异常处理、跨域配置和接口返回封装等基础能力。
　　数据持久层选用MyBatis-Plus。系统中存在任务流转、积分流水、家庭成员绑定和统计查询等多类数据操作，完全手写单表CRUD会带来较多重复代码，而JPA在复杂SQL调优上不够直观。MyBatis-Plus既能通过通用Mapper减少基础操作代码，又保留手写SQL的灵活性，因此更适合本系统的开发节奏。
1.5.2前端与 CSS 框架：UniApp 和 TailwindCSS
　　移动端选用UniApp 3.0。该框架支持一套代码编译到H5、Android和小程序等平台，能够降低多端维护成本。Vue 3的Composition API便于把登录、任务、计时和角色切换等逻辑按功能组织，Pinia则用于保存用户角色、任务状态和模式切换信息，使家长端与儿童端在同一工程中保持相对清晰的状态边界。
　　界面样式采用TailwindCSS。该框架通过原子类快速调整间距、颜色、圆角和布局，适合移动端组件的细粒度适配。对于儿童端而言，按钮尺寸、留白、颜色对比和动效节奏都需要反复微调；TailwindCSS可以减少样式文件切换成本，并通过按需打包控制页面资源体积。
1.5.3权限管理技术：Sa-Token
　　权限管理方面，系统涉及管理员、家长和儿童三类角色，且不同角色的数据边界必须清楚。Spring Security功能完整，但配置成本相对较高；本项目选择Sa-Token，主要是因为其登录态管理、权限注解和Redis接入方式较轻量，适合在有限开发周期内实现接口级鉴权。
　　Sa-Token在本系统中主要承担登录会话创建、Token校验和权限判断。用户登录后，后端写入对应会话状态；业务接口通过拦截器和权限注解进行访问控制。接入Redis后，登录态和权限信息可以集中缓存，便于移动端和管理后台在不同账号体系下保持隔离。
1.6主要研究内容
　　本系统旨在解决ADHD中小学生在日常任务执行中的启动困难、持续困难和反馈不足问题，同时弥补现有工具在家长协同和数据追踪方面的不足。围绕这一目标，本文从工程实现和理论转化两个层面展开研究：
　　第一，将心理学原则转化为前端交互。围绕降低认知负荷、代币奖励和及时正向反馈，设计任务卡片、专注计时、星星奖励和儿童端低干扰界面，并在UniApp页面中实现相应组件。
　　第二，验证前后端分离架构在多角色场景下的可行性。系统通过Spring Boot 3、Sa-Token和Redis实现登录状态、接口权限和防重复提交控制，并结合测试数据观察其在并发访问下的稳定性。
　　第三，探索大语言模型在家庭辅助场景中的边界。系统将AI模块设计为旁路服务，由后端定时聚合任务和情绪数据，生成家长建议与儿童鼓励文本，同时保留兜底话术，避免外部模型失败影响主业务。
　　第四，完成从需求分析、表结构设计、接口开发、前后端联调到Docker部署和自动化测试的完整工程流程，并对关键实现进行记录，为后续扩展硬件端和更多干预策略提供基础。

2系统分析
　　本章围绕系统分析展开，重点回答两个问题：其一，现有技术条件是否能够支撑本系统实现；其二，儿童、家长和管理人员分别需要哪些功能边界。分析结果将作为后续架构设计、数据库建模和接口开发的依据。
2.1可行性分析
　　“小步（Small Steps）”系统在开发实施前，从技术可行性、操作可行性与理论可行性三个维度进行了系统评估，以下分别阐述。
2.1.1技术可行性
　　技术可行性方面，系统选用的Spring Boot 3、MyBatis-Plus、Vue 3、UniApp、PostgreSQL和Redis均为较成熟的开发方案，相关文档和社区案例较多。对于毕业设计而言，这些技术既能覆盖多端开发、权限控制和缓存需求，也便于在有限时间内完成联调和测试。
　　后端以Spring Boot 3和MyBatis-Plus构建业务接口与持久层，移动端以UniApp和Vue 3实现H5及移动端页面，数据库使用PostgreSQL保存任务、积分和家庭数据，Redis用于会话缓存和防重复提交。上述组合与项目已有模块划分相匹配，技术风险总体可控。
2.1.2操作可行性
系统面向两类目标用户：ADHD儿童（约6至15岁）及其家长。
　　儿童端操作可行性主要依赖低认知负荷设计：单屏只突出当前任务，大按钮和高辨识图标减少阅读压力，复杂配置尽量放到家长端完成。这样可以避免儿童在执行任务前就被设置项和页面跳转消耗注意力。
　　家长端和管理后台则采用相对常规的交互模式。家长端保留任务创建、奖励配置和数据查看入口，管理后台使用Element Plus实现表格、表单和菜单管理。这种设计能降低成人用户学习成本，也便于后续维护。
2.1.3理论指导可行性
　　本系统的设计并非纯粹的工程实现，其底层以心理学与教育学理论为指导，以确保功能设计不偏离干预目标。主要参考的理论方向包括：
　　其一是认知负荷理论。ADHD儿童的工作记忆容量本就有限，界面信息过载极易导致认知超载。因此在设计中贯彻"认知卸载"原则——单屏仅呈现一项任务、采用低饱和度配色、减少非必要文字信息。
　　其二是脚手架理论（Scaffolding Theory）[9]，即在学习者能力不足时提供临时性支持，待其逐步掌握后渐进撤除辅助。系统通过AI识别儿童在具体任务中的障碍点，提供针对性的辅助建议，待儿童熟练后逐步减少干预强度，帮助其从外部监管过渡到自我管理。
　　其三是操作性条件反射理论与家庭系统视角。系统通过及时、可累积的星星奖励强化目标行为，同时把部分提醒和记录功能交给系统承担，减少家长直接催促造成的对立感，使家长更容易转向陪伴和协作。
2.2系统需求分析
　　需求分析的核心目标是明确系统的功能边界与质量约束。以下从目标用户群体、功能需求与非功能性指标三个维度进行分析。
2.2.1目标用户群体分析
　　系统的目标用户主要分为两类：ADHD儿童（被辅助方）与家长（辅助方）。两类用户对软件的功能期待与交互需求存在显著差异，需分别进行分析。
（1）儿童用户特征
通过在特教机构的陪读观察，发现该年龄段ADHD儿童具有以下显著特征：
　　注意力集中程度高度依赖任务的趣味性。儿童在游戏或短视频场景中可维持长时间的高度专注（即"超聚焦"现象），但在刷牙、收拾书包、背诵课文等日常任务中，专注持续时间往往不足五分钟。
　　时间感知能力薄弱。儿童对任务所需时长缺乏基本预估能力，执行过程中普遍存在拖延现象，往往在截止时间临近时才出现紧迫感。情绪反应迅速但耐挫能力不足。微小的执行失误即可引发强烈的情绪反应，表现为放弃任务或攻击性行为。
　　因此，儿童端的设计底线为三条：零学习成本、容错性高、即时正向反馈。界面风格不应呈现为效率工具，而应更接近于理解其心理特征的游戏化交互界面。
（2）家长用户特征
养育ADHD儿童的家长长期承受较大的身心压力。通过社群调研，发现其核心痛点主要集中在以下几个方面：
　　一是监督疲劳。家长每日需反复进行相同的任务督促——"去刷牙"、"坐好"、"别磨蹭"，长期持续后极易产生情绪耗竭，进而引发家庭冲突。
　　二是信息不对称。儿童反馈的"做完了"未必反映真实执行情况，家长对任务实际耗时、执行过程中是否存在中断等关键信息缺乏了解渠道。
　　三是缺乏可操作的指导策略。家长并非缺乏干预意愿，而是缺乏具体的干预方法——在儿童情绪崩溃时应如何回应、如何沟通，需要的是可直接应用的策略建议。
　　还有就是想要实在的建议。家长不是不想好好管，是真不知道怎么管。孩子崩溃的时候该说什么话、怎么接，他们需要的是这种能直接拿来用的东西。
因此，家长端的功能设计需围绕以下核心需求展开：行为数据可视化、任务便捷下发、系统定期提供实用建议。其定位相当于为家长配备外部认知辅助与情绪调节支持。

2.2.3非功能性需求分析
除功能需求外，系统还需满足一系列非功能性指标要求，以保障用户体验与系统稳定性。
（1）性能和响应时间
　　打卡接口：专注模式结束时需同步状态并结算代币，涉及跨库操作，核心接口的响应时间需控制在150毫秒以内（P99），以保证动画切换的流畅性。
　　大模型异步处理：AI寄语的生成通常需要10至30秒，该过程不得阻塞主线程，需通过消息队列或定时任务异步执行，确保用户界面的正常响应。
　　并发能力：晚间8时至9时为作业高峰时段，系统需具备单节点每秒1000次请求的承载能力，以应对流量峰值。
（2）系统安全性和隐私保护
　　未成年人数据隔离：ADHD属于敏感健康信息，数据库设计应遵循最小化采集原则。涉及儿童姓名、生理特征等敏感字段需在入库前进行哈希或加密存储。
API防重放和防篡改：前端发起的写操作请求需携带时间戳与签名校验，防止伪造请求导致的代币异常刷取。
　　角色越权防护：基于Sa-Token的RBAC模型进行权限校验，在路由层拦截的基础上，业务逻辑层进行二次验证。例如，家长账号仅能查询其名下绑定的儿童数据，无法通过修改ID访问其他家庭的数据。
（3）可用性与兼容性
　　跨终端一致性：UniApp编译生成的应用包需在主流安卓设备上保持布局一致性，尤其是TailwindCSS实现的圆角效果需保持渲染质量，并需适配刘海屏与沉浸式状态栏。
　　弱网环境适应性：在WiFi信号较弱或断网环境下，儿童端的倒计时等本地功能需保持正常运行。任务进度先进行本地离线存储，待网络恢复后自动静默同步至服务端。

图 3.1 总体架构设计
3.1.1架构分层设计
“小步”系统在架构设计上采用经典的分层架构思路，各层职责明确、边界清晰。自上而下分为四层[11]。
　　表现层包括移动端应用和Web管理后台。移动端承载儿童端与家长端两类界面，负责把用户操作转换为HTTP请求，并将任务、积分和建议等后端数据渲染为可理解的界面；管理后台则面向管理员，侧重列表、表单和统计图表。
　　业务逻辑层基于Spring Boot 3实现，是任务流转、积分计算、家庭绑定和AI反馈的主要处理位置。Controller负责接收请求，Service完成业务规则校验和状态更新，必要时由Manager或异步任务协调外部服务调用。
　　数据访问层通过MyBatis-Plus连接业务对象和数据库表。常规单表操作由通用Mapper处理，复杂统计和联表查询保留手写SQL，以便在性能和可维护性之间取得平衡。
　　基础层包括PostgreSQL、Redis、日志组件和大模型API代理。PostgreSQL保存任务、积分、家庭和情绪等核心数据；Redis用于登录态、热点查询和防重复提交；外部AI接口通过后端统一代理，避免直接暴露在前端。
3.1.2前后端分离协同
　　“小步”系统采用前后端分离部署方式。移动端和管理后台通过HTTP接口访问后端服务，后端统一返回JSON数据，并用Result结构封装状态码、提示信息和业务数据。该设计便于移动端、后台和后端分别开发，也方便在联调阶段定位接口和权限问题。
3.2核心业务模块设计
3.2.1用户认证与鉴权模块
系统涉及三种角色：管理员、家长与儿童。权限隔离机制基于Sa-Token实现[13]。
（1）登陆认证
　　前端提交账号密码进行身份验证，后端验证通过后在Redis中创建用户会话上下文，并将Token返回至前端。
（2）双域隔离设计
　　为避免管理后台账号与移动端账号混用，系统使用Sa-Token的多账号体系，将Admin端和App端的登录态缓存分开维护。这样即使两个端都使用Token机制，也能在缓存Key、权限集合和拦截规则上保持隔离。
（3）细粒度权限管控
　　业务层接口执行前，会经过 Sa-Token 全局拦截器（Global Interceptor）。通过在业务特定的 Controller 方法上注入@SaCheckRole("PARENT")与@SaCheckPermission("task:create")等鉴权注解，保证例如儿童不可创建或随意删除高优任务，家长不能跨家庭体系查看其他儿童数据，实现角色与组织层的严格互斥。
3.2.2任务管理与流程设计
　　任务是系统最核心的业务实体，几乎所有功能模块均围绕其展开。鉴于ADHD儿童在任务执行过程中的状态变化具有较大不确定性，任务状态机的设计保留了适度的弹性空间。
　　任务状态包括以下四种：未开始、执行中（进入番茄钟计时状态）、已完成（打卡提交成功）、已废弃（当日未完成且已过期）。
　　家长创建任务时，除填写标题与预计耗时外，还需配置以下关键属性：执行周期（单次/每日循环/自定义频率）与完成后奖励的代币数量。
　　此外，复杂任务支持挂载子步骤清单。该设计主要基于ADHD儿童面对"大任务"时易产生畏难心理的特点，将其拆解为若干小步骤后可有效降低心理压力。
3.2.3专注模式与时间管理
专注模块为儿童进入任务后的计时体验提供支撑。该模块不涉及持久层的写入操作，优先保证前端的运行流畅性。
　　专注模式的流程为：儿童选择任务后，前端读取任务ID、倒计时参数和奖励信息；点击“开始”后，Pinia状态切换为专注状态，倒计时开始运行。在该状态下，页面会拦截返回和Tab切换操作，尽量维持连续的任务环境。
　　若倒计时自然结束，前端将完成记录（包含持续时长、设备信息等）提交至后端，后端开启事务确认任务完成并同步核算奖励。
　　若中途退出，前端仍会将实际积累的时长传回后端，后端在归档时标记为“非完全完成”。该部分数据对后续AI分析儿童的专注耐受阈值与情绪变化趋势具有参考价值。
3.2.4智能辅助生成与数据反馈
　　为减轻家长长期撰写鼓励话术的负担，系统将AI反馈设计为旁路流程[14]。后端定时任务汇总儿童当天的任务完成情况、专注时长和情绪记录，再调用大语言模型生成建议。该流程不阻塞儿童打卡、家长点亮和积分结算等主业务。
　　每日固定时段，系统提取某一儿童与家长组合的近十天打卡记录（包括总完成数、成功率、超时情况、情绪评分等），聚合成结构化的行为摘要JSON。
随后，将该摘要与管理后台预设的Prompt模板组合，异步发送至大语言模型。
　　大模型返回文本会先经过脱敏和长度校验，再写入数据库。家长端次日可在首页看到“辅助指引卡片”，确认合适后再同步给儿童端。通过这一确认环节，系统避免把未经家长判断的生成内容直接推送给儿童。
3.3数据库设计
　　数据库设计需要同时服务任务执行、积分结算、家庭关系和情绪记录。对于本系统而言，数据表不只是保存结果，还要支持后续追踪儿童在哪些任务环节出现停顿、家长如何调整奖励规则，以及积分变化是否可回溯。
3.3.1设计原则与总体架构
　　在概念建模阶段，系统从需求描述中抽取用户、儿童档案、家长任务、儿童任务记录、积分账户、奖励、情绪记录等实体，并梳理它们之间的一对多或多对一关系，形成后续关系表设计的基础。
　　高内聚与领域划分原则。围绕系统核心业务，将数据划分为“用户与档案”、“任务流转”、“激励体系”与“情绪与AI追踪”四大领域，保证各模块职责清晰、边界明确。
　　读性能优先原则。针对儿童端与家长端的高频读取场景，通过适度去范式化设计与缓存机制，减少多表关联查询带来的性能开销。
　　灵活扩展原则。对于任务子步骤、用户偏好等非结构化数据，采用 PostgreSQL 的 JSONB 类型存储，以适应未来业务变化。
数据一致性保障原则。通过快照字段与流水表设计，确保积分、奖励等关键数据具备可追溯性与审计能力。

3.3.4缓存策略与 Redis 结构设计
　　系统存在多处高频访问场景，例如移动端页面切换时的Token校验、任务列表读取、积分余额查询和完成按钮提交。若全部直接访问PostgreSQL，会增加数据库压力，因此系统引入Redis作为缓存和短期互斥控制层。
　　认证缓存：系统配合Sa-Token在Redis中保存用户登录态、权限集合和过期时间。接口拦截时优先读取缓存，减少重复查询数据库的开销。
　　任务防重复提交：儿童端完成任务时，后端利用Redis短期Key和SETNX语义建立临时互斥标记。若用户因网络延迟或连续点击发送多次请求，后续请求会被拦截，从而避免积分重复结算。

4.2.1安全认证与路由拦截的实现细节
　　用户登录时，请求先进入服务层校验账号、密码和角色状态。验证通过后，后端调用Sa-Token创建登录会话，并将Token写入响应头返回给前端。后续请求携带该Token访问业务接口，拦截器会在进入Controller之前完成登录态校验。与手动拼接JWT相比，这种方式减少了会话过期、续期和缓存维护的重复代码。
　　@Configurationpublic class SaTokenConfigure implements WebMvcConfigurer {
@Override

4.2.2结构化任务与分发系统的业务逻辑实现
　　任务系统的产生和流转涉及大量的数据库事务一致性（Transaction Consistency）。以“家长为儿童当天新建任务”这一核心业务场景为例： 在对应的TaskController中暴露 POST 请求接口。该请求包含被控端儿童 ID、任务元数据及预期所需时段。 在TaskServiceImpl逻辑中，由于此操作同时牵涉向任务模版表task_info插入源数据，以及在任务实体日志表task_daily_log预生成当日的待办占位记录，为了防止网络中断造成的数据不一致（如：主模版建立但今日待办未生成），整个 Service 方法使用了 Spring 框架提供的@Transactional(rollbackFor = Exception.class)注解进行事务包裹。另外，为实现 MyBatis-Plus 赋能的高级表关联查询，系统针对家长端“查看孩子近一周所有已排期任务”需求，利用 MyBatis-Plus 的QueryWrapper构建了类型安全的条件筛选：

log.error("Error in task breakdown for task: {}", taskName, e);
return getMockTaskBreakdown(taskName, taskDesc, childAge);
}
}
　　AI调用失败时，系统不会中断家长端页面加载，而是从预设话术库中选取兜底文本返回。生成内容入库前会替换儿童真实姓名等敏感信息，避免把个人信息直接暴露在外部模型调用链路中。

5系统测试
　　系统测试的目的在于验证核心流程是否稳定、权限边界是否可靠，以及性能是否满足设计约束。由于“小步”系统面向儿童和家庭数据，测试不仅关注功能是否可用，还关注越权访问、重复提交和弱网恢复等场景。
5.1测试环境与策略构建
5.1.1测试环境说明
为确保测试结果尽可能接近真实使用场景，搭建了独立的预发布测试环境：
　　后端测试环境采用Docker部署PostgreSQL 15和Redis 7，并启动Spring Boot后端服务；移动端以H5形式在PC浏览器和华为P40 Pro、Mate 30 Pro等设备上验证；管理后台使用Chrome浏览器进行功能和兼容性测试。
5.1.2测试维度设计
本次测试从以下三个维度展开：
　　功能逻辑验证：从家长创建任务开始，到儿童接收、执行完成，再到AI反馈生成，验证整条业务链路的完整性与连贯性，排查流程中的断点或异常。
　　交互体验验证：测试按钮响应、页面跳转、倒计时恢复、任务提交和奖励反馈是否符合预期。自动化测试使用Playwright覆盖管理后台UI和H5移动端主要页面。
　　性能压力验证：围绕登录、任务列表、打卡提交和积分查询等接口进行并发测试，重点观察打卡接口P99延迟、登录接口QPS和缓存命中情况。
5.2核心业务功能测试
5.2.1多角色权限与路由测试
　　本节主要验证Sa-Token权限隔离机制的有效性。系统涉及管理员、家长、儿童三种角色，不同角色的接口调用权限与数据访问范围需严格隔离。
　　横向越权测试：使用儿童账号的Token，构造POST请求访问家长端的任务创建接口。后端返回状态码403，提示权限不足，表明注解拦截机制生效。
　　纵向越权测试：使用家长A的Token，尝试查询家长B名下绑定的儿童数据。后端返回空数组，表明底层数据隔离拦截器正常工作，未允许跨家庭数据访问。
综合来看，Sa-Token与自定义拦截器的组合在权限隔离方面表现稳定。
5.2.2任务生命周期状态扭转测试
本节验证任务从创建到完成的完整生命周期中，状态变迁与数据落库的正确性。
　　任务生命周期测试以一条“限时5分钟”的扫地任务为例。家长端创建任务后，儿童端刷新出现待办卡片；儿童点击开始后任务进入执行中状态；完成并提交后，家长端进行点亮确认，系统再完成积分结算和流水写入。
　　测试过程中尝试将应用切换至后台挂起，数十秒后切回前台，倒计时显示的时间按自然时间差递减，未出现计时暂停或错乱现象。
　　倒计时结束后，系统自动播放成功音效并发起打卡提交请求。经数据库验证，代币余额更新正确，与任务配置的奖励数额一致。
整条链路测试结果表明，任务生命周期的状态推演与设计文档一致，数据回溯完整，未发现遗漏环节。
5.2.3核心接口性能压力测试

6	总结与展望
　　本文围绕ADHD儿童家庭中常见的任务执行困难，设计并实现了“小步”行为习惯辅助系统。系统以儿童端、家长端和管理后台三端协同为基础，将任务拆解、专注计时、积分奖励、家长点亮和AI建议整合到同一业务流程中。
　　确立了“无压力”的UI交互设计哲学。摒弃具有威慑感的设计风格，转而通过游戏化代币的正向激励与大语言模型的情感化话术构建闭环干预机制。
　　首先，系统完成了前后端分离架构的工程实现。后端基于Spring Boot 3、MyBatis-Plus和Sa-Token实现业务接口与权限控制，前端基于UniApp、Vue 3和Pinia实现多端页面与状态管理，数据库和Redis支撑任务、积分和会话数据。
　　其次，系统验证了AI辅助反馈在该场景中的可用性。大语言模型并未直接替代家长决策，而是作为建议生成工具，为家长提供鼓励话术和观察角度；同时通过异步调用、脱敏和兜底文本控制风险。
6.1总结
　　项目实施过程中也暴露出一些工程问题。例如，早期联表查询较多，接口响应不够稳定；引入Redis承担会话缓存和去重锁后，性能得到改善。前端为了降低儿童端操作复杂度，减少了路由跳转和设置入口，这增加了状态管理难度，但换来了更低的使用门槛。
6.2系统存在的不足与未来研究展望
　　虽然“小步”系统在实验室层面通过了测试并在核心架构上奠定了长远发展的框架，但在迈向下一代商业化级产品的路上，依然具有部分可深挖的研究点：
　　多维度数据联动仍有不足。目前系统主要依赖儿童主动打卡和家长确认，数据来源较单一。后续可以接入智能手表或ESP32硬件端，通过蓝牙或本地传感器获取活动状态、心率等辅助信息，再与任务完成记录交叉分析。
　　大模型本地化也是后续方向之一。当前AI建议依赖云端接口，存在延迟、费用和隐私方面的限制。未来可以在内网服务器或边缘终端部署轻量模型，使敏感数据尽量留在本地，并降低长期使用成本。
　　科学技术的价值不仅在于提升效率，更在于为那些不易被大众关注的群体建立平等的支持系统。“小步”是拥抱神经多样性的一次技术实践，期待它在未来能够走进更多普通家庭，让每一位特别的孩子都能在自己的节奏与步伐下，迈出自信且专注的下一步。

## 输出格式要求
你必须且只能输出一个合法的JSON数组，不要包含任何其他文字说明。
每个数组元素包含以下三个字段：
- desc: 步骤描述（不超过20个字）
- duration_sec: 建议用时（整数，单位：秒）
- voice: 语音引导语（不超过30个字）
""";
/**
* 用户Prompt模板（User Prompt）
* 使用占位符，运行时替换为实际的上下文信息
*/
　　public static final String USER_PROMPT_TEMPLATE = """
请将以下任务拆解为适合ADHD儿童执行的微步骤。
## 任务信息
- 任务名称：{task_title}
- 儿童年龄：{child_age}岁
- ADHD类型：{adhd_type}
## 输出要求
请以JSON数组格式输出，每个元素包含desc、duration_sec、voice三个字段。
## 输出示例
[
{
            "desc": "把铅笔和橡皮放在桌面上",
"duration_sec": 30,
"voice": "先把铅笔和橡皮拿出来，放在桌上哦！"
},
{
"desc": "打开数学课本翻到第12页",
"duration_sec": 60,
"voice": "找到数学课本，翻到第12页，你真棒！"
}
]
现在请拆解任务：{task_title}
""";
/**
* 构建最终的用户Prompt
*/
public static String buildUserPrompt(String taskTitle, int childAge,
String adhdType) {
String adhdTypeDesc = switch (adhdType) {
case "I" -> "注意力不集中型（容易走神、遗忘）";
case "H" -> "多动冲动型（坐不住、易冲动）";
case "C" -> "混合型（兼具注意力不集中和多动冲动特征）";
default -> "未指定";
};
return USER_PROMPT_TEMPLATE
.replace("{task_title}", taskTitle)
　　                .replace("{child_age}", String.valueOf(childAge))
.replace("{adhd_type}", adhdTypeDesc);
}
/**
* 构建完整的消息列表（用于OpenAI API的messages参数）
*/
public static String buildMessages(String taskTitle, int childAge,
String adhdType) {
return """
[
{
"role": "system",
"content": %s
},
{
"role": "user",
"content": %s
}
]
""".formatted(
escapeJson(SYSTEM_PROMPT),
escapeJson(buildUserPrompt(taskTitle, childAge, adhdType))
);
}
/**
* JSON字符串转义工具方法
*/
private static String escapeJson(String input) {
return input
                .replace("\\", "\\\\")
.replace("\"", "\\\"")
.replace("\n", "\\n")
.replace("\r", "\\r")
.replace("\t", "\\t");
}
